01 · android_security_architecture

Android security architecture

Android's core assumption is refreshingly pessimistic: every app is potentially hostile, and so is every input it processes. Security is therefore built as defense in depth — independent layers, each of which must be defeated separately. A bug in one layer should be contained by the next.

Click each layer below to expand it. Notice the pattern: the higher layers make fine-grained, user-visible decisions; the lower layers make coarse, non-negotiable ones.

USER SPACEApps & the App Sandbox▸

Every app runs as its own Linux user (UID) in its own process, with private data in /data/data/<pkg>. Apps cannot read each other's files or memory. Sandboxing is enforced by the kernel, not by the app — an app cannot "forget" to be sandboxed.

MECHANISMS: per-app UID · seccomp-bpf syscall filter · SELinux untrusted_app domain
FRAMEWORKAndroid Framework & Permissions▸

System services (ActivityManager, PackageManager…) check Android permissions on every sensitive API call. This is where "Allow this app to access your location?" is decided and where signature levels, appops and user consent live.

MECHANISMS: install-time & runtime permissions · permission checks over Binder · AppOps
IPCBinder IPC▸

Almost every privileged action is really a Binder call to a system service. The Binder kernel driver attaches the caller's real UID/PID to each transaction, so services can reliably ask "who is calling me?" before acting. Covered in depth in section 05.

MECHANISMS: kernel-supplied caller credentials · SELinux binder_call checks
KERNELLinux Kernel: DAC + SELinux (MAC)▸

The kernel enforces two independent gates on every access: classic discretionary UNIX permissions (DAC), and mandatory SELinux policy (MAC). Both must say yes. Even a process running as root is still confined by SELinux.

MECHANISMS: UID/GID/mode bits · SELinux type enforcement · seccomp · namespaces
BOOTVerified Boot (AVB)▸

Each boot stage cryptographically verifies the next, from an immutable ROM root of trust up through the kernel and system partitions (dm-verity). Tampered system images fail to boot or boot with a warning — persistence for attackers becomes very hard.

MECHANISMS: chain of trust · dm-verity · rollback protection
HARDWARETEE / StrongBox & hardware keys▸

A separate execution world (ARM TrustZone TEE) or a discrete secure chip (StrongBox) holds cryptographic keys and biometric matching. Even a fully compromised Android kernel cannot extract these keys. Covered in section 06.

MECHANISMS: TrustZone · KeyMint · Gatekeeper · Keystore attestation

The five pillars to remember

📦
IsolateApp sandbox: one UID + one SELinux domain per app.
🎫
Grant minimallyPermissions gate APIs; least privilege by default.
🛂
Verify the callerBinder delivers trustworthy caller identity to services.
⛔
Mandate policySELinux applies to everyone — root included.
🔐
Anchor in hardwareBoot integrity and keys rooted below the OS.
WHY LAYERS, NOT ONE BIG WALL?

A media-parsing bug (remember Stagefright?) may give an attacker code execution inside the media process — but that process sits in a tight SELinux domain with a seccomp filter, no network sockets, and no access to app data. The exploit succeeds; the attack still fails. That is defense in depth working as designed.

02 · linux_permissions_vs_android_permissions

Linux permissions vs Android permissions

Classic Linux permissions answer: "which user may touch this file?" Android permissions answer a completely different question: "which app may use this capability?" Android's clever trick was to reuse the first system to build the second.

Linux DAC in 30 seconds

Every file has an owner (UID), a group (GID) and a 9-bit mode: read/write/execute for user / group / other (rwxr-x---). Every process runs as some UID/GID; the kernel compares them on each access. It's called Discretionary Access Control because the owner may change these bits at their discretion — chmod 777 and everyone is invited.

Android's twist: one UID per app, not per human

A phone has one human but thousands of mutually distrusting apps. So at install time, installd assigns each package its own UID (u0_aXXX, numerically 10000+). The "user" being isolated from other "users" is the app itself. Press install below and watch the sandbox form:

Android permissions: capability tickets

File bits can't express "may use the camera" or "may read SMS" — those aren't files, they're services. So Android adds a second, higher-level permission system declared in the manifest (<uses-permission>) and checked by system services on every call.

PROTECTION LEVELGRANTEDEXAMPLE
normalAutomatically at install — low risk.INTERNET, VIBRATE
dangerousBy the user, at runtime, revocable in Settings.CAMERA, ACCESS_FINE_LOCATION, READ_CONTACTS
signatureOnly to apps signed with the same key as the definer.OEM / system app APIs
signature|privilegedSignature, or preinstalled in /system_ext/priv-app + allowlisted.INSTALL_PACKAGES

The two worlds even connect: a few Android permissions are implemented as Linux groups. Granting INTERNET simply adds the app's process to GID inet (3003), and the kernel refuses socket creation to anyone outside that group. Elegant reuse.

LINUX (DAC)

  • Subject: a user/process UID
  • Object: files & file-like things
  • Granularity: r / w / x
  • Decided by: file owner (discretionary)
  • Checked by: the kernel, per syscall
  • root bypasses it entirely

ANDROID PERMISSIONS

  • Subject: an app (package + UID)
  • Object: capabilities / APIs (camera, SMS, location…)
  • Granularity: named permissions, per-feature
  • Decided by: platform + user consent
  • Checked by: system services on each Binder call
  • Revocable at runtime; visible in Settings
COMMON TRAINEE CONFUSION

"The app has root because I ran adb root" ≠ "the app can do anything." On Android, DAC (even as root), Android permissions, and SELinux must all agree. That third gate is the subject of the next two sections.

TRY IT ON CUTTLEFISH
$ adb shell id                                  # the shell user: uid=2000(shell), note its groups
$ adb shell dumpsys package com.android.settings | grep -A4 "grantedPermissions\|runtime permissions"
$ adb shell pm list permissions -g -d           # all dangerous permissions, grouped
$ adb root && adb shell ls -ln /data/data | head # every app dir owned by a distinct 10xxx UID
$ adb shell pm grant <pkg> android.permission.CAMERA   # grant/revoke a runtime permission from the shell
03 · selinux_mac_te_mls

SELinux: MAC, Type Enforcement & MLS

DAC has two fatal flaws: owners can weaken it (chmod 777), and root ignores it completely. SELinux fixes both with Mandatory Access Control (MAC): a system-wide policy, written by the platform vendor, loaded at boot, that nobody — not app authors, not users, not root — can loosen at runtime. If the policy has no rule allowing an access, the access fails. Full stop.

Default: DENY

SELinux is a whitelist. Anything not explicitly allowed by a rule is denied. Contrast with DAC's "allowed unless a bit forbids it".

Enforcing

Denials are blocked and logged. Production Android runs enforcing, always, since Android 5.0.

Permissive

Denials are logged but permitted — a development aid on userdebug builds (setenforce 0), never shipped.

Everything gets a label

SELinux decisions are made on security contexts (labels), not on names or UIDs. Every process, file, socket and property carries one. Tap each part of this real label (an app's data file on Cuttlefish) to decode it:

u:object_r:app_data_file:s0:c112,c256
Tap a colored segment ↑

Type Enforcement — the engine that does 99% of the work

Type Enforcement (TE) is beautifully simple: give every process a type (called its domain, e.g. untrusted_app, system_server, mediaserver) and every object a type (e.g. app_data_file, camera_device). Then the entire policy is just statements of the form:

allow <domain> <type> : <class> { permissions };

"Processes of domain X may perform these operations on objects of type Y." Identity (UID) stops mattering; what kind of thing you are is all that matters. Two facts follow:

  • A root process in a weak domain is still weak — uid=0 buys nothing against TE.
  • Compromising a process only yields that domain's allowed accesses. The blast radius is written down in the policy, and reviewable.

MLS — the second dimension

Multi-Level Security adds the trailing s0:c… field. Classic MLS models military clearance levels (secret, top-secret); Android keeps everything at one sensitivity, s0, but repurposes MLS categories as per-app isolation tags. Each app's processes and files get a category pair derived from its UID (e.g. c112,c256). The MLS constraint requires the process's categories to dominate (⊇) the file's categories — so even though all apps share the untrusted_app type, app A still cannot read app B's files. It's a kernel-level second fence around the sandbox, and it also separates Android multi-user profiles (work vs personal). Try it:

Process (app): reads file of:
MENTAL MODEL

TE separates kinds of processes (apps vs system vs media). MLS categories separate instances of the same kind (this app vs that app, this user profile vs that one). Together with per-app UIDs, that's a three-lock sandbox.

TRY IT ON CUTTLEFISH
$ adb shell getenforce                       # Enforcing
$ adb shell ps -AZ | grep untrusted_app       # app domains + per-app categories
$ adb shell ls -Z /data/data/com.android.chrome   # file labels match the app's categories (needs adb root)
$ adb shell id -Z                             # the shell's own context: u:r:shell:s0
# userdebug builds only — flip modes to see logging vs blocking (never in production):

$ adb shell setenforce 1
04 · sepolicy_allow_neverallow

SEPolicy: allow rules & neverallow rules

SEPolicy is the concrete body of rules that SELinux enforces on Android. In AOSP it lives in system/sepolicy/ (platform policy) plus per-device additions under the vendor tree, written mostly in .te files, compiled at build time and loaded by init before anything else runs.

Anatomy of an allow rule

allow untrusted_app app_data_file:file { read write open getattr }; │ │ │ │ └─ permissions granted │ │ │ └─ object class (file, dir, socket, binder…) │ │ └─ target type (the object's label) │ └─ source domain (the process's label) └─ grant keyword — SEPolicy is additive: rules only ever ADD access

Supporting cast you'll meet in real policy: attributes (named sets of types, like appdomain — one rule can cover every app domain), macros (domain_auto_trans, r_dir_file…), type_transition rules (which domain a new process enters when init execs a binary), and labeling maps: file_contexts, seapp_contexts, property_contexts, service_contexts.

neverallow — executable code review

A neverallow is the opposite of a rule: it's an assertion checked at build time. If any allow rule anywhere — including a vendor's — would grant the forbidden access, the build fails. Google also enforces core neverallows on real devices via CTS. They encode Android's non-negotiables:

neverallow untrusted_app tee_device:chr_file { read write }; neverallow { appdomain -shell } kmem_device:chr_file ~getattr; neverallow * self:capability sys_module; # no one loads kernel modules at runtime

So: allow rules grant, neverallow rules guard the granters. A vendor can extend policy for their HALs, but cannot punch holes through the platform's guarantees.

The access decision — run it yourself

This simulator plays the kernel's role (the "security server"). Pick a source domain, a target type and a permission, then request access. Watch what happens at the policy gate — and read the avc: line it produces, because decoding these denials is 80% of real-world SELinux work.

THE audit2allow TRAP

    
audit2allow converts denials into candidate allow rules — a great reading aid and a terrible authoring policy. Blindly pasting its output grants exactly what the (possibly malicious, possibly mislabeled) access attempted, and will often collide with a neverallow at build time — which is the system telling you the design, not the policy, is wrong.

05 · binder_ipc_security

  
Binder IPC security

  
Sandboxed apps can do almost nothing alone — every camera frame, location fix or SMS goes through a system service in another process. The channel for all of it is Binder, a kernel driver (/dev/binder) purpose-built for fast, object-capability IPC. Which makes Binder the security chokepoint of Android: if a service can't tell who's calling, permissions are theater.


  
Why Binder identity can be trusted

  
When a client transacts, the Binder kernel driver itself stamps the transaction with the sender's real UID and PID, taken from kernel task structures. Userspace cannot forge these — a malicious app can lie in the payload, but not in the envelope. On the service side, Binder.getCallingUid() returns that kernel-attested identity, and permission checks build on it.

The layered checks on every privileged call

  
    
    
  • 1 · Reachability. Can the client even talk to this service? servicemanager only hands out service handles allowed by service_contexts policy, and SELinux checks binder { call transfer } between the two domains.
    • 
    
  • 2 · Kernel-attested identity. The driver attaches the real caller UID/PID to the transaction.
    • 
    
  • 3 · Service-side permission check. context.enforceCallingPermission(...) / checkCallingPermission(...) maps that UID to granted Android permissions and throws SecurityException on failure.
    • 
    
  • 4 · Interface token. Each AIDL transaction begins with the interface descriptor, blocking cross-interface confusion.
    • 
  


  

    
CLASSIC PITFALL: IDENTITY LAUNDERING

    
A service doing work on behalf of a caller must not accidentally use its own powerful identity for the caller's request — the "confused deputy" bug. The API pair to know: clearCallingIdentity() / restoreCallingIdentity(), which make the service's deliberate self-actions explicit. Forgetting to check getCallingUid() before clearing it is a recurring real-world CVE pattern.

06 · keystore_keymint_hardware_keys

  
Keystore, Keymaster/KeyMint & hardware-backed keys

  
Everything so far protects a running system. Keystore protects secrets even when the system loses. The design goal is one sentence: apps can use cryptographic keys, but nothing in Android — not the app, not root, not even the kernel — can ever read the raw key bytes.


  
Who's who

  

    
COMPONENTWHEREROLE

    
Android Keystore APIApp processWhat developers call: KeyGenParameterSpec, KeyStore.getInstance("AndroidKeyStore"). Hands back an opaque handle, never key material.

    
keystore2System daemon (Rust)Gatekeeper of handles: per-app key namespaces, enforces which UID may use which key, talks to the HAL. Replaced the old keystore daemon in Android 12.

    
KeyMint HALHAL boundaryThe contract for "do crypto with keys you keep". Successor of the Keymaster HAL (Keymaster 4 → KeyMint 1 in Android 12) — you'll hear both names.

    
TEE (TrustZone)Secure world, same SoCIsolated execution environment running a trusted OS (e.g. Trusty). Default home of "hardware-backed" keys.

    
StrongBoxDiscrete secure chipSeparate tamper-resistant processor with its own CPU/RAM/storage. Strongest tier; resists even physical attacks.

What "hardware-backed" buys you

  
    
    
  • Non-exportability. The API can mark keys as usable-only-inside-hardware; Android gets an opaque handle and an encrypted key blob that only KeyMint can unwrap.
    • 
    
  • Authorization enforced below the OS. Key properties travel with the key: "only for signing", "only after fingerprint auth in the last 30 s" (setUserAuthenticationRequired), "only these digests/paddings". The TEE enforces them even against a rooted Android.
    • 
    
  • Key attestation. KeyMint signs a certificate chain, rooted in a Google/OEM key, proving to a remote server: this key lives in real hardware, on a device with verified boot state X. Servers can refuse keys from compromised devices.
    • 
    
  • Rollback resistance & version binding. Keys are bound to OS/patch level, so downgrading the OS to a vulnerable build can't unlock them.
    • 
  


  

    
THE FULL-STACK PICTURE

    
Notice how the sessions' pieces snap together for one payment: the app's sandbox holds its state; a runtime permission gated the fingerprint sensor; the auth token crossed Binder with a kernel-attested UID; SELinux lets only keystore2 reach the KeyMint HAL (with neverallows keeping apps away from tee_device); and the signature happened in silicon Android can't read. Defense in depth, end to end.

07 · check_yourself

  
Check yourself

  
Three quick questions — each targets a misconception we see every cohort.

  


  

    
1 · A process on Android is running as root (uid=0). Which statement is true?

    
    
    
    
Root defeats DAC only. MAC doesn't care about UID 0 — the process's domain decides what it may touch. This is precisely why Android runs enforcing everywhere.

  


  

    
2 · All third-party apps run in the untrusted_app domain. What stops app A reading app B's files via SELinux?

    
    
    
    
Type Enforcement separates kinds; MLS categories separate instances of the same kind. Plus distinct Linux UIDs underneath — a multi-lock sandbox.

  


  

    
3 · Why can a system service trust Binder.getCallingUid() but not a uid field inside the request payload?

    
    
    
    
Kernel-attested envelope vs attacker-controlled letter. Every permission check in the framework rests on this distinction.

  




  

    
4 · An AVC denial shows the correct source domain but an unexpected target type. What should you investigate first?

    
    
    
    
A wrong target type usually means a labeling problem. Fix the label before changing policy; otherwise you authorize the wrong design.

  


  

    
5 · A navigation app needs vehicle speed for route estimation. What is the safer architecture?

    
    
    
    
The trusted service mediates access, verifies the caller, limits the exposed data and keeps direct hardware access outside the app domain.

  


  

    
6 · What does a neverallow rule do?

    
    
    
    
neverallow is an executable policy assertion checked during compilation; it prevents vendors or later rules from violating platform guarantees.

  


  

  
One-screen cheat sheet

  

    
DAC vs MACDAC: owner-set, root bypasses. MAC (SELinux): vendor policy, default-deny, binds everyone including root.

    
labeluser:role:type:mls → u:r:untrusted_app:s0:c112,c256. Type does the work; categories isolate app instances.

    
allow ruleallow src_domain target_type:class { perms }; — additive, whitelist-only.

    
neverallowBuild-time (and CTS-tested) assertion that no allow may ever grant this. Guards the guarantees.

    
avc: deniedRead scontext → tcontext → tclass → perm. First ask: wrong label, or missing rule?

    
App sandboxper-app UID + untrusted_app domain + MLS cats + seccomp. Four fences, one app.

    
Android permissionManifest-declared capability ticket, checked by services on Binder calls; dangerous ones need runtime consent.

    
Binder identityDriver-stamped UID/PID → getCallingUid() → enforceCallingPermission(). Beware clearCallingIdentity ordering.

    
Keystore chainApp API → keystore2 → KeyMint HAL → TEE/StrongBox. Keys are used, never seen. Attestation proves it remotely.

10 · aaos_security_architecture

    
AAOS security architecture: Android, extended into the vehicle

    
Android Automotive OS inherits Android's security model rather than replacing it. The automotive extension adds trusted car framework services and a vehicle abstraction boundary. The crucial design rule is that a normal car app should consume Car APIs; it should not become a direct VHAL client or a raw vehicle-bus client.

    
V3 mental model: Android security protects the compute platform. AAOS then adds another mediation path before requests reach vehicle-facing code. A compromised infotainment app must not automatically become a compromised vehicle network.

  


  

    
    
    
    
    
    
    
  

  
Car App. Runs under the ordinary Android sandbox. Its UID, Android permissions and SELinux domain remain the first containment boundary.


  

    

      
WHAT TRANSFERS DIRECTLY FROM ANDROID
Per-app UID sandboxing, Binder caller credentials, framework permissions, SELinux MAC/TE/MLS, Verified Boot, Keystore2/KeyMint and platform/vendor separation.

      
WHAT AAOS ADDS
Car APIs and CarService, vehicle properties, AIDL VHAL, area IDs, occupant zones, multi-display/user behavior, vehicle-network integration and OEM-specific vehicle services.

    

    
GENERIC CUTTLEFISH ≠ AUTOMATICALLY AAOS

11 · car_api_carservice_aidl_vhal

    
Car APIs, CarService & the AIDL Vehicle HAL

    
The Vehicle HAL exposes the vehicle as typed properties that can be read, written or subscribed to when supported. For car applications, AOSP's model is deliberately mediated: apps use Car APIs such as CarPropertyManager; Car Service is the Java VHAL client, and SELinux blocks ordinary apps from connecting directly to the VHAL.

    
Since Android 13, the modern VHAL is AIDL-based at IVehicle.aidl; new VHAL implementations are expected to use the AIDL interface. Property configuration also defines access mode, change mode, data type and areas.

  


  

    
PERF_VEHICLE_SPEEDGlobal, continuous, read-only. App-facing read access requires the car speed permission.

    
INFO_VINVehicle identity data. Treat as privileged/sensitive vehicle information.

    
HVAC / SEAT / DOORMany properties are zoned. Area IDs distinguish seats, doors, windows and other physical regions.

    
VENDOR PROPERTIESOEM-defined properties must still respect access control, stable boundaries and least privilege.

THE AAOS RULE TO REMEMBER
Car app → Car API → CarService → VHAL. Do not “fix” access problems by turning an app into a direct VHAL client or granting raw vehicle device access. AOSP explicitly recommends Car APIs for car apps, and SELinux blocks direct app-to-VHAL access.

12 · aaos_oem_vendor_selinux

    
OEM / vendor SELinux: protect the integration boundary

    
Automotive builds contain substantial OEM code: vehicle HALs, vendor daemons, device nodes, diagnostics and hardware-specific services. SELinux is where the product architecture becomes enforceable. Platform policy provides Android-wide guarantees; device/vendor policy adds only the access the hardware integration actually requires.

  


  

    
PLATFORM SIDE
  • system / system_ext / product
  • Car framework & system services
  • Platform SELinux policy / neverallows
  • Stable framework/HAL contracts

    
STABLE / REVIEWED BOUNDARY

    
VENDOR SIDE
  • vendor services and HALs
  • OEM vehicle hardware implementation
  • Vehicle device nodes / bus adapters
  • Device-specific SELinux policy

  


  

    
Case A · wrong label
Vehicle data file appears as unlabeled after an OTA.

    
Case B · app wants VHAL
Third-party app requests direct access to IVehicle.

    
Case C · vendor daemon
OEM daemon genuinely needs one device-node ioctl.

  

  
Select a case. The goal is to fix the architecture or label first, then add the smallest policy change only when the access is genuinely required.


  

    
AUTOMOTIVE audit2allow TRAP
Vendor integration can generate noisy AVCs. Treat audit2allow as a decoder, not an approval engine. A broad vehicle-service allow rule can turn an infotainment compromise into access to vehicle-facing resources.

    

      
AAOS SELINUX EVIDENCE LAB

      
$ adb shell ps -AZ | grep -Ei 'car|vehicle|vhal'

$ adb root && adb shell dmesg | grep 'avc: denied' | tail -20
$ adb shell ls -lZ /vendor/bin/hw | grep -i vehicle
$ adb shell dumpsys car_service --list
# Correlate process domain → Binder/service name → VHAL/vendor component → target label.

    

  







  

    
13 · aaos_multi_user_occupant_zones

    
Users, displays & occupant zones

    
Cars are shared devices. AAOS commonly runs a headless system user in the background for system services while human drivers/passengers use regular or guest users. An occupant zone represents a physical location in the vehicle and maps that zone to displays and other resources; multi-display systems can therefore have separate user journeys at the same time.

  


  

    
DRIVER ZONE
Driver · User 10Main display · driver audio zone
ClusterDriver-facing display / privileged surfaces

    
AAOS USER + OCCUPANT MAPPING
Headless User 0→system services
Occupant zone 0→User 10 · Display 0
Occupant zone 1→User 11 · Display 3
Audio zone↔occupant zone

    
PASSENGER ZONE
Passenger · User 11Passenger display · separate user data
Remote interactionsRequire explicit automotive privileges/APIs

  


  

    
OCCUPANT-ZONE SECURITY PUZZLE

    
A passenger app wants to control playback on another occupant zone. What is the right model?

    

    
Choose the architecture, not a privilege shortcut.

14 · vehicle_network_trust_boundary

    
Beyond AAOS: the vehicle gateway is another security domain

    
SELinux can strongly confine Android processes, but it does not authenticate a CAN frame, segment Automotive Ethernet, authorize an ECU diagnostic session or validate a gateway routing policy. The boundary after the VHAL/vendor implementation needs its own controls. Treat the in-vehicle network as a separate security domain, not as “the bottom of Android.”

  


  

    
AAOS COMPUTE
  • App sandbox
  • CarService permissions
  • Binder identity
  • SELinux domains
  • VHAL mediation

    
TRUST BOUNDARY

    
VEHICLE GATEWAY
  • Message allowlists
  • Segmentation / routing
  • Diagnostics policy
  • Rate / anomaly controls
  • Domain separation

    
NETWORK BOUNDARY

    
ECU / DOMAIN
  • CAN / LIN / Ethernet
  • Body / powertrain / ADAS
  • ECU authorization
  • Secure diagnostics
  • Safety constraints

END-TO-END MENTAL MODEL
A secure vehicle architecture has multiple independently enforceable trust boundaries: Android app isolation, trusted AAOS service mediation, VHAL/vendor separation, gateway/network controls and ECU-local authorization. No single boundary should be treated as a universal security control.
