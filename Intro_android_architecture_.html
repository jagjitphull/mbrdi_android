Vocabulary first

Six terms that prevent 80% of the confusion

Android
The broad operating-system platform and ecosystem. A commercial device usually combines open-source Android components with OEM and possibly Google components.
AOSP
The Android Open Source Project: the open-source platform code that OEMs and integrators can build and customize.
Android Auto
A phone-powered projection experience. The phone runs the app and projects a driver-optimized experience to a compatible vehicle display.
Android Automotive OS (AAOS)
Android running directly on vehicle hardware, typically as the in-vehicle infotainment operating system. It does not require a connected phone to be the computer.
Google built-in / GAS
Google apps and services supplied for some AAOS vehicles. AAOS can exist without Google built-in; the two are not synonyms.
Car Service + VHAL
The framework-side automotive service layer and the vehicle hardware abstraction layer that represent vehicle functions as controlled properties.
Myth buster: “Android in a car” does not automatically mean Android Auto. It may be projected Android Auto, embedded AAOS, an OEM Android fork, or simply an Android tablet mounted in the cabin.

Core concept

Android architecture, one layer at a time

Think of Android as a large hotel. Apps are guests. Framework APIs are the front desk. System services are specialized departments. Binder is the internal telephone network. HALs are standardized loading docks. The Linux kernel is the building’s utilities, locks, and machinery.

Important architecture correction: the stack is not a simple “top calls the layer immediately below” ladder. Android is a network of processes. Binder IPC frequently crosses process boundaries, native daemons can talk to HALs, and kernel interfaces support all layers.

The invisible wiring

Binder IPC: Android’s internal service bus

Most important Android components live in separate processes. Binder lets a client call a remote service with an interface that can feel like a local method call. AIDL describes many of those interfaces; the Binder kernel driver transports transactions.

Try the mental movie: a vehicle HMI asks for speed. The app-facing manager does not jump straight to an ECU. Follow the call across controlled process boundaries.

Identity travels

The service can identify the caller’s UID/PID and enforce permissions rather than trusting every caller.

Failures are boundaries

A dead remote process can trigger a Binder death notification instead of silently behaving like an in-process object.

Not a network protocol

Binder is mainly local IPC. Vehicle Ethernet, CAN, Bluetooth, Wi‑Fi, and cellular are separate communication domains.

Boot story

From power-on to an interactive Android system

The exact boot chain varies by device, but this simplified sequence is a useful diagnostic model.

1. Boot ROM / bootloaderEstablish trust and load boot components
2. Linux kernelInitialize memory, scheduler, drivers
3. initParse rc files, mount partitions, start daemons
4. ZygotePreload classes and fork app processes
5. system_serverStart framework services
6. UI readySystem UI, launcher, apps, vehicle HMI
Vehicle twist: a car cannot behave like a phone that simply boots when the user presses a power button. AAOS must coordinate ignition, wake, suspend, shutdown preparation, Garage Mode, and power policy with a vehicle controller through the VHAL.
Automotive extension

What AAOS adds around the Android core

The familiar Android stack remains, but AAOS adds a car framework and integration surfaces for a shared, multi-display, power-sensitive machine connected to many non-Android ECUs.

Vehicle properties

VHAL represents functions as typed properties with access mode, change mode, area/zone, and value metadata. It abstracts the underlying bus—not the permission model.

Power coordination

AAOS coordinates with the vehicle controller for ON, shutdown preparation, suspend/hibernate, wake, and power policies for components such as display, audio, radios, and CPU.

Shared cabin

Multiple users, displays, occupants, audio zones, microphones, and input devices are normal—not edge cases.

Do not blur these concepts

Security, driving safety, and functional safety are different

Security

Protect confidentiality, integrity, and availability using app UIDs, permissions, SELinux, sandboxing, Verified Boot, signing, encryption, and secure updates.

Driver distraction safety

Limit what can be displayed or entered while moving. Apps and system UI must react to driving state and UX restrictions.

Functional safety

Systematic assurance that safety-related functions behave acceptably under faults. AAOS infotainment is not automatically the controller for braking, steering, or propulsion.

Architecture rule: Never assume that a VHAL property means an unrestricted app can control the corresponding physical function. Permissions, Car Service policy, OEM gateways, network segmentation, domain controllers, and safety mechanisms should all constrain the path.
