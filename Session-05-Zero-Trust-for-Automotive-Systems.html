What does “never trust, always verify” actually mean?

Think of the vehicle as a secure building. An ECU does not receive every key just because it is already inside. Each door checks its badge, its job, and whether anything suspicious has happened.

🔑
Identity is the badge.

Attestation checks whether the person carrying it still looks and behaves as expected.

Every service request is evaluated using ECU identity, certificate validity, runtime evidence, requested service, trust state, vehicle mode, and an explicit policy rule. Network location alone contributes no automatic authorization.

The lab separates the policy decision point from the nftables policy enforcement point.

A production design should bind workload identity to hardware-protected key material, freshness-protected evidence, signed software baselines, bounded authorization policies, and deterministic degraded behavior. The enforcement action must be constrained by safety analysis rather than copied from enterprise IT quarantine patterns.

Trust scoring is a policy abstraction, not a standardized automotive metric.

1. Zero Trust principles for connected vehicles

The central idea is simple: being “inside the car” is not sufficient evidence. Every requested communication is evaluated using identity, device integrity, requested service, operational context and policy.

01

Verify explicitly

Authenticate the ECU and service, validate runtime evidence, and inspect context before granting access.

  • Certificate identity
  • Fresh attestation nonce
  • Software measurement
  • Vehicle mode and risk
02

Least privilege

Permit only the smallest required service flow, for the shortest useful time, between named identities.

  • ADAS → powertrain API only
  • No broad “zone-to-zone allow”
  • Separate diagnostics policy
  • Expire temporary grants
03

Assume breach

Design as though one ECU or app may already be compromised. Contain the blast radius and preserve safe vehicle behavior.

  • Microsegments
  • Continuous telemetry
  • Dynamic restriction
  • Fail-safe, not blindly fail-open

Simple analogy

🏢
A secure building, not a gated village

Passing the outer gate does not grant access to the control room. Each door checks identity, authorization and current risk. Automotive Zero Trust applies the same logic to ECUs and services.

Automotive adaptation

Enterprise Zero Trust often focuses on users and applications. A vehicle also needs deterministic timing, intermittent connectivity, safety priorities, hardware-rooted identity, service-oriented communication and carefully designed degraded modes.

Myth: “Zero Trust means trusting nothing, so the vehicle cannot operate offline.”
Reality: it means no implicit trust. Local policy decision and enforcement points can operate offline using cached, bounded policies and local evidence. Cloud reachability should not be a universal dependency for safety-critical operation.
Myth: “A valid certificate automatically authorizes every service.”
Reality: a certificate proves identity within a trust domain. Authorization is a separate policy decision. Lab 2 deliberately shows why a CA-signed but unapproved ECU identity still requires an allowlist or policy check.

3. Mutual ECU authentication

Server-only TLS is insufficient when both endpoints are machines. Mutual TLS makes the client ECU and server ECU prove possession of private keys tied to trusted certificates.

Important separation: mTLS authentication answers “who is this peer?” The policy engine still must answer “may this peer call this service now?”
Protocol distinction: this lab uses mTLS for an Automotive Ethernet-style service. On CAN or FlexRay, AUTOSAR SecOC protects PDU authenticity and freshness using authenticators and freshness values; it is not a mutual TLS session handshake and does not itself provide payload confidentiality.

4. Runtime attestation and continuous monitoring

Authentication identifies the ECU. Attestation adds evidence about the software and boot state that ECU is currently running. Continuous monitoring keeps re-evaluating that evidence after the session starts.

Fresh nonce

The verifier sends a random one-time value. This prevents a previously valid attestation response from being replayed.

Runtime evidence

The ECU reports boot state, software measurements, configuration and relevant security events.

A device-bound key signs the nonce and measurements. The verifier checks signature, freshness and baseline policy.

5. Policy-based communication and ECU trust scoring
A trust score is not a universal automotive standard. It is one possible policy abstraction. The useful part is not the number itself—it is the transparent evidence, thresholds, decision and enforcement action.
100
NORMAL
All evidence satisfies the training policy.
80–100 · Normal
Approved least-privilege flows remain available.
60–79 · Restricted
Only the policy/evidence service is reachable; normal egress is blocked.
0–59 · Quarantine
Source and destination traffic is dropped, subject to separately engineered safety exceptions.
Safety warning: a real vehicle must not mechanically apply a generic IT quarantine rule to safety-critical ECUs. Enforcement requires hazard analysis, fail-operational/fail-safe design, bounded fallback behavior and coordination with functional-safety engineering.



6. Cuttlefish as the Android/IVI evidence source
Cuttlefish is used here for Android framework and boot-state evidence. The Linux namespace topology simulates the other ECU zones because Cuttlefish networking varies by release and launch configuration.

Userdebug nuance
A Cuttlefish userdebug or eng image may intentionally be unlocked or report a non-green state. The lab profile records this as a development exception. The production profile requires green verified boot, locked flash and a user build.
Do not teach the wrong lesson: “orange on Cuttlefish” does not automatically mean the VM was compromised. It can reflect the expected development build posture. Policy must understand the declared environment.

#!/usr/bin/env python3
"""Training-grade ECU trust scorer and optional nftables policy actuator."""
from __future__ import annotations

import argparse
import json
import subprocess
import sys
from dataclasses import asdict, dataclass


@dataclass(frozen=True)
class Evidence:
    ecu_id: str
    ip: str
    attestation_valid: bool
    certificate_valid: bool
    secure_boot: bool
    patch_age_days: int
    anomaly_events: int
    replay_events: int


def calculate_score(e: Evidence) -> tuple[int, list[str]]:
    score = 0
    reasons: list[str] = []

    if e.attestation_valid:
        score += 30
    else:
        reasons.append("attestation failed")

    if e.certificate_valid:
        score += 20
    else:
        reasons.append("certificate invalid or expired")

    if e.secure_boot:
        score += 15
    else:
        reasons.append("secure boot evidence absent")

    if e.patch_age_days <= 30:
        score += 15
    elif e.patch_age_days <= 90:
        score += 8
        reasons.append("patch level aging")
    else:
        reasons.append("patch level outside policy")

    score += max(0, 15 - min(e.anomaly_events, 5) * 3)
    if e.anomaly_events:
        reasons.append(f"{e.anomaly_events} anomaly event(s)")

    score += max(0, 5 - min(e.replay_events, 5))
    if e.replay_events:
        reasons.append(f"{e.replay_events} replay event(s)")

    return max(0, min(score, 100)), reasons


def decision(score: int) -> str:
    if score >= 80:
        return "NORMAL"
    if score >= 60:
        return "RESTRICTED"
    return "QUARANTINE"


def run_nft(args: list[str], tolerate_failure: bool = False) -> None:
    cmd = ["ip", "netns", "exec", "zt-gw", "nft", *args]
    result = subprocess.run(cmd, text=True, capture_output=True)
    if result.returncode and not tolerate_failure:
        raise RuntimeError(result.stderr.strip() or "nft command failed")


def apply_policy(ip: str, state: str) -> None:
    # Delete is deliberately tolerant because the element might not exist.
    run_nft(["delete", "element", "inet", "zt_vehicle", "restricted_v4", "{", ip, "}"], True)
    run_nft(["delete", "element", "inet", "zt_vehicle", "quarantined_v4", "{", ip, "}"], True)

    if state == "RESTRICTED":
        run_nft(["add", "element", "inet", "zt_vehicle", "restricted_v4", "{", ip, "}"])
    elif state == "QUARANTINE":
        run_nft(["add", "element", "inet", "zt_vehicle", "quarantined_v4", "{", ip, "}"])


SCENARIOS = {
    "healthy": Evidence("adas-01", "10.77.20.2", True, True, True, 10, 0, 0),
    "degraded": Evidence("adas-01", "10.77.20.2", True, True, True, 75, 5, 0),
    "compromised": Evidence("adas-01", "10.77.20.2", False, True, False, 130, 5, 3),
}


def main() -> int:
    parser = argparse.ArgumentParser()
    parser.add_argument("--scenario", choices=SCENARIOS, default="healthy")
    parser.add_argument("--evidence-json", help="Read evidence from a JSON file instead of a built-in scenario")
    parser.add_argument("--apply", action="store_true", help="Apply the decision to the zt-gw nftables sets")
    args = parser.parse_args()

    if args.evidence_json:
        with open(args.evidence_json, encoding="utf-8") as handle:
            evidence = Evidence(**json.load(handle))
    else:
        evidence = SCENARIOS[args.scenario]

    score, reasons = calculate_score(evidence)
    state = decision(score)
    report = {"evidence": asdict(evidence), "score": score, "decision": state, "reasons": reasons}
    print(json.dumps(report, indent=2))

    if args.apply:
        try:
            apply_policy(evidence.ip, state)
        except (OSError, RuntimeError) as exc:
            print(f"[FAIL] Could not apply nftables policy: {exc}", file=sys.stderr)
            return 2
        print(f"[PASS] Applied {state} policy to {evidence.ip}.")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
