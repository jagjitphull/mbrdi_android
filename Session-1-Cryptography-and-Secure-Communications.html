01

Symmetric and asymmetric cryptography

One shared secret versus a keypair. The interesting part is not the maths — it is that the two solve completely different problems and every real protocol uses both, because asymmetric crypto is roughly three orders of magnitude too slow to encrypt a video stream.

The division of labour

Symmetric ciphers move bulk data. Asymmetric primitives solve the two things symmetric crypto cannot: agreeing a key with someone you have never met, and proving who you are to someone who only knows your public key. Every session in this document follows the same shape — an asymmetric handshake that costs milliseconds, followed by symmetric bulk encryption that costs nanoseconds per block.

SymmetricAsymmetric
Key modelOne secret, both parties hold itPrivate key never leaves the holder; public key is published
WorkhorsesAES-256-GCM, ChaCha20-Poly1305, AES-XTS (disk)X25519, ECDH P-256, Ed25519, ECDSA, RSA-PSS

AEAD is the only acceptable symmetric mode

Encryption without authentication is a vulnerability, not a feature. A raw CTR- or CBC-mode ciphertext can be modified by an attacker who cannot read it — flip a bit in the ciphertext and you flip the corresponding plaintext bit. AEAD (Authenticated Encryption with Associated Data) binds a 128-bit authentication tag to both the ciphertext and to unencrypted context you want to pin down, such as a packet header or a version number.

Step 1 — Key and nonce. The key is long-lived; the nonce must be unique for every single message under that key. Not secret. Unique.
The nonce-reuse cliff. Reuse a nonce with the same key in GCM and you do not lose a little security, you lose all of it. XOR the two ciphertexts and the keystream cancels, revealing the XOR of the plaintexts. Worse, an attacker can recover the GHASH authentication subkey H and forge arbitrary tags from then on. This is why TLS 1.3 derives the nonce from a per-record sequence number rather than trusting an implementer to pick one.
🔮 Predict before you test
One bit of an AES-GCM ciphertext is changed in transit. What should a secure receiver do?
AES-GCM verifies the authentication tag before releasing plaintext. A changed bit makes the entire operation fail.

Note the length arithmetic. 16 bytes of plaintext produced 32 bytes out: GCM is a stream mode, so ciphertext length equals plaintext length, plus a fixed 16-byte tag. If you ever see AEAD output that is a multiple of the block size, someone has silently swapped you onto CBC.

Key agreement: X25519 in thirty seconds

Diffie-Hellman lets two parties who have exchanged only public values compute the same secret. Neither secret key crosses the wire, and an observer who records the whole exchange still cannot derive the result. Ephemeral DH — a fresh keypair per session, thrown away afterwards — is what gives you forward secrecy: compromising a long-term key tomorrow does not decrypt traffic captured today.

Never use a raw DH output as a key. The shared secret is a curve point, not uniformly random bytes, and it has algebraic structure. Always run it through a KDF — HKDF-Extract then HKDF-Expand with a context label. TLS 1.3 does exactly this, and Module 04 shows the label strings.
Threat model — what symmetric crypto does not buy you
  • Unauthenticated DH is trivially MITM-able. Anonymous X25519 gives you a private channel with somebody. Without a signature binding the ephemeral key to an identity, that somebody may be the attacker. This is precisely why the TLS 1.3 server signs its handshake transcript.
  • Confidentiality is not integrity. AES-CTR without a MAC lets an attacker set any plaintext bit they can locate, without the key.
  • Key separation. One key, one purpose. Never use a signing key for encryption or a session key for two directions — TLS 1.3 derives separate client and server traffic secrets for this reason.
  • Side channels. A table-driven AES implementation leaks the key through cache timing. Use AES-NI/ARMv8-CE, or a constant-time design like ChaCha20 where hardware AES is absent.
60-second recapCryptographic division of labour
  • AEAD encrypts and authenticates; nonce reuse can collapse both properties.
  • Ephemeral key agreement creates forward secrecy, but authentication is still required to stop a MITM.
  • Raw DH output must pass through a context-bound KDF before becoming traffic keys.
Explain it to a colleagueAsymmetric cryptography establishes or authenticates the session because the peers do not yet share a secret. Symmetric cryptography then carries bulk data because it is dramatically faster.
Knowledge check 01

A logging service encrypts each record with AES-256-GCM, using a counter for the nonce that resets to zero whenever the process restarts. What is the most severe consequence?

Records become slightly compressible, leaking length information
The GHASH subkey can be recovered, letting an attacker forge valid tags for arbitrary messages

The nonce being public is irrelevant; it must be unique. Reuse under the same key exposes the XOR of two plaintexts and, critically, permits recovery of the authentication subkey H — which collapses integrity, not just confidentiality. A restart-safe design uses a random 96-bit nonce or persists the counter.

Why does TLS not simply use RSA or ECDH to encrypt the whole data stream and skip symmetric ciphers?

Asymmetric algorithms cannot encrypt more than one block, ever
Export regulations forbid it
Public-key operations are ~1000× slower per byte, and RSA can only encrypt data smaller than its modulus

Cost and structural limits. Public-key operations are orders of magnitude slower and RSA is bounded by the modulus size. Forward secrecy comes from ephemeral asymmetric key agreement — the opposite of option D.

02

Hashing and digital signatures

A hash compresses any input to a fixed fingerprint. A signature makes a fingerprint unforgeable. Android's entire boot chain and its whole app distribution model are built out of nothing but these two ideas, repeated at every layer.

What a cryptographic hash must guarantee

PropertyDefinitionWhat breaks if it fails
Preimage resistanceGiven H(x), infeasible to find xPassword hashes fall; PCR values reveal measurements
Second preimageGiven x, infeasible to find x' ≠ x with the same hashAnyone can substitute a malicious system.img for a signed one
Collision resistanceInfeasible to find any pair collidingAttacker gets a benign artefact signed, then swaps in the twin — this is how SHA-1 died
AvalancheOne input bit flips ~half the output bitsPartial-match attacks; dm-verity tampering becomes locally detectable but globally guessable
MD5 and SHA-1 are dead for signatures. SHA-1 chosen-prefix collisions cost a few tens of thousands of dollars of GPU time (SHA-1 is Shattered, 2017; chosen-prefix 2020). They survive only in legacy non-security roles such as git object naming. Use SHA-256 or SHA-384. Use SHA-3 or BLAKE2 when you need a different construction, not because SHA-2 is weak.

Hash, MAC, signature — three different jobs

These get conflated constantly. The distinction is who can produce the value and who can check it.

KeyWho can produce itWho can verify · gives you
HashNoneAnyoneAnyone. Integrity only against accident, never against an attacker who can also rewrite the hash.
HMACShared secretAnyone holding the keyAnyone holding the key. Integrity + authenticity, but no non-repudiation — the verifier could have forged it.
SignaturePrivate keyOnly the private key holderAnyone with the public key. Integrity + authenticity + non-repudiation.
Why HMAC exists and H(key ‖ message) does not. The Merkle–Damgård construction behind SHA-256 leaks its internal state in the digest, so given H(secret ‖ m) an attacker can compute H(secret ‖ m ‖ padding ‖ extension) without knowing the secret. That is a length-extension attack. HMAC's nested two-key construction blocks it. SHA-3 and BLAKE2 are immune by design and can safely be keyed directly.

Signatures: ECDSA vs Ed25519

Both are elliptic-curve signature schemes at roughly the 128-bit security level, but they differ in one operationally critical way: where the per-signature random value k comes from.

The ECDSA nonce trap. ECDSA needs a secret random k per signature. If k repeats across two signatures, the private key falls out of simple algebra — this is exactly how the PlayStation 3 signing key was recovered in 2010, and how a long line of Bitcoin wallets have been drained by Android's broken SecureRandom in 2013. Ed25519 derives k deterministically from the key and message hash, removing the entire failure class. Prefer Ed25519 where you have the choice; use RFC 6979 deterministic ECDSA where you do not.

Knowledge check 02

An API authenticates requests with token = SHA256(api_secret ‖ request_body). What is the specific attack?

Rainbow-table lookup of the secret
Timing attack on the string comparison only
Length extension — append data to the body and compute a valid token without knowing the secret

SHA-256 is Merkle–Damgård, so the digest is the internal state after processing the input. An attacker resumes from it, appends chosen bytes, and produces a token that validates. HMAC-SHA-256 — or SHA-3/BLAKE2 keyed directly — fixes it.

You are reviewing firmware that signs update manifests with ECDSA P-256 on a device with no hardware RNG and a predictable early-boot entropy pool. What is the highest-severity finding?

P-256 is too small; migrate to P-521
A repeated or biased ECDSA nonce k allows full private-key recovery from two signatures
Signature verification will be too slow at boot
DER encoding of the signature is variable-length

Weak entropy plus ECDSA is the classic catastrophic pairing — two signatures with the same k yield the private key by algebra. P-256 itself is fine. Remediate with RFC 6979 deterministic ECDSA or Ed25519.

Your team wants non-repudiation on device telemetry so a manufacturer cannot later deny a reading originated from their fleet. HMAC or signature?

Signature — with HMAC the verifier holds the same key and could have forged the value
HMAC — it is faster and equally binding
Either; both are keyed and therefore equally non-repudiable
Neither; only a hash chain provides non-repudiation

Non-repudiation requires that only one party could have produced the value. Symmetric keys are held by both sides, so an HMAC proves nothing to a third party.

03

PKI, certificates and chains of trust

A signature only tells you a key signed something. A certificate is the mechanism that lets you decide whether you care about that key — by transferring trust from an anchor you already accept.

What a certificate actually is

An X.509 certificate is a signed assertion binding a public key to an identity, with a validity window and a set of constraints on what the key may be used for. The signature comes from the issuer. Verification is recursive: check the leaf's signature with the issuer's key, check the issuer's certificate with its issuer's key, until you reach a self-signed root that is in your trust store because you put it there.

Trust anchors are configuration, not cryptography. Nothing mathematically distinguishes a root CA certificate from any other self-signed certificate. It is trusted purely because it sits in the store. On Android this matters a great deal: since Android 7, apps do not trust user-installed CAs by default, which is exactly why intercepting an app's TLS traffic on Cuttlefish requires either a debuggable build with a network_security_config or a system-store injection.
Step 1 — The anchor. A self-signed root. Its authority comes from being installed, nothing else.
CN is dead; only SAN counts. Since RFC 6125 and enforced by every modern client, hostname matching reads subjectAltName exclusively. A certificate with the hostname only in the Common Name will be rejected by Chrome, by Android's NetworkSecurityConfig, and by Go's TLS stack — even though openssl verify says OK, because openssl verify checks the chain, not the name.

Revocation, and why it barely works

Revocation is the weakest joint in PKI. CRLs are large and stale. OCSP leaks the browsing target to the CA and adds a blocking round trip, so most clients soft-fail — meaning an attacker who can block OCSP simply gets the certificate accepted. OCSP stapling with the must-staple extension is the only variant that hard-fails safely. The pragmatic industry answer has been to shorten lifetimes instead. CA/Browser Forum ballot SC-081v3 cut the maximum public TLS certificate lifetime from 398 days to 200 days on 15 March 2026, with 100 days following on 15 March 2027 and 47 days on 15 March 2029. At 47 days a revoked certificate expires before most CRL consumers would have noticed it — which is the point.

Threat model — PKI failure modes seen in the wild
  • Rogue or coerced CA. Any of the ~150 anchors on the device can mint a certificate for any name. Mitigate with Certificate Transparency logs and, for your own endpoints, pinning.
  • Name-constraint absence. Most intermediates carry no nameConstraints, so a compromised enterprise sub-CA can issue for anything.
  • Confused-deputy EKU. A cert issued for clientAuth accepted as a server certificate by a lax stack.
  • Pinning done wrong. Pin the leaf's key and a certificate rotation bricks the fleet. Pin an intermediate's SPKI plus a backup pin, and set an expiry.
  • Private key exfiltration. The reason Module 06 exists: a key in a file can be copied; a key in a TPM or StrongBox cannot.

04

TLS 1.3 and mutual TLS

TLS 1.3 is not TLS 1.2 with better defaults. It is a smaller protocol built by deletion: every legacy key exchange, every non-AEAD cipher, renegotiation and compression were removed, and the handshake was restructured so encryption starts one round trip earlier.

What was removed, and why each removal killed a real attack

Deleted in TLS 1.3The attack it enabled
Static RSA key transportNo forward secrecy — one stolen server key retroactively decrypts years of captured traffic
CBC-mode and all non-AEAD ciphersBEAST, Lucky13, POODLE — padding-oracle and MAC-then-encrypt failures
RC4, 3DES, export ciphersRC4 biases; Sweet32; FREAK and Logjam downgrade-to-export
CompressionCRIME, BREACH — compression ratio as a plaintext oracle
RenegotiationTriple Handshake and renegotiation-injection attacks
Custom / weak DH groupsLogjam. TLS 1.3 permits only named groups: X25519, P-256, P-384, and the ML-KEM hybrids
Only five cipher suites remain, and they no longer name the key exchange or the authentication method — those are negotiated separately in extensions. Session resumption and the 0-RTT trade-off

After a handshake the server issues a session ticket. Resumption uses a PSK derived from the previous connection and skips certificate exchange entirely. 0-RTT goes further: the client sends application data in its very first flight, encrypted under a key derived from the PSK alone.

0-RTT early data is replayable, by design. There is no server contribution to the key yet, so nothing binds that data to a live handshake. An attacker who captures a 0-RTT flight can replay it repeatedly. Only ever send idempotent requests as early data — never a POST, never a state-changing API call. Servers should implement single-use ticket tracking, but you cannot rely on that across a load-balanced fleet. 0-RTT also has no forward secrecy against a compromise of the ticket key.

Mutual TLS

In ordinary TLS the client authenticates the server and the server has no idea who the client is — application-layer credentials fill that gap. mTLS moves client identity into the transport: the server sends a CertificateRequest, and the client answers with its own certificate and a CertificateVerify over the transcript. The client's private key never moves, so a stolen credential store yields nothing replayable, unlike a bearer token.

In TLS 1.3, what stops an active attacker from substituting their own ephemeral key share and man-in-the-middling the connection?

The ClientHello is encrypted
X25519 shares are validated against the certificate's public key
The session ticket binds the connection to a prior handshake
CertificateVerify signs the handshake transcript, binding the ephemeral share to the certified identity

This is the whole point of CertificateVerify. The transcript hash covers the ServerHello and its key_share, so a substituted share invalidates the signature. Anonymous ECDHE without it is trivially MITM-able.

Why WireGuard's Noise_IK handshake is worth understanding

Step 1 — Pre-shared knowledge. Unlike TLS, there is no discovery phase. Each peer already holds the other's public key, so there is nothing to negotiate and nothing to downgrade.
MAC1 and the silence property. Every initiation packet carries a MAC computed over the responder's public key. Threat model — tunnel deployments
  • Over-broad AllowedIPs. The single most common WireGuard misconfiguration, and it silently disables the inbound source filter.
  • Key material in config files. wg0.conf holds the private key in cleartext. It needs 0600 and a umask 077 at creation, and it should never reach a backup or a git repo.

Everything so far assumed the software checking a signature was itself trustworthy. This module is about earning that assumption — and about the one thing software can never do, which is keep a secret from the machine it runs on.

TPM: what it is actually for

A TPM is a slow, cheap, tamper-resistant coprocessor with three jobs: hold keys that cannot be extracted, maintain PCRs, and sign statements about those PCRs. It is not an accelerator — it is deliberately slow. Its value is entirely in what it refuses to do.

Cuttlefish: secure_env is a real TEE substitute

Cuttlefish does not fake hardware-backed keys. The host runs a secure_env process holding a software TPM, and the guest's KeyMint and Gatekeeper HALs talk to it over virtio sockets. Keys are wrapped by that TPM, so from the guest's perspective they genuinely never appear in guest memory.

When you are testing an app's attestation logic on Cuttlefish, this is the first divergence from real hardware you will hit.

Key attestation: proving a key is where you think it is

The problem: an app generates a keypair and sends the public key to a server. How does the server know the private key is in hardware and not in a rooted emulator's heap? Answer: the key is generated inside KeyMint, which issues a certificate for it, signed by a factory-provisioned attestation key, chaining to a Google root. The attestation certificate carries an extension describing the key's properties — and critically, the device's verified boot state and vbmeta digest.

Follow the dependency backwards and the whole session closes into a loop: the attestation is an ECDSA signature (Module 02), delivered in an X.509 chain (Module 03), transported over TLS to your backend (Module 04), and it asserts a vbmeta digest produced by a Merkle tree of SHA-256 hashes (Module 02) rooted in a key the silicon will not surrender.

Threat model — the limits of hardware trust
  • A TPM proves state, not intent. Correctly measured, correctly signed malware still attests as GREEN if it was signed by a trusted key.
  • Sealing is brittle by design. A firmware update legitimately changes PCR values and your sealed disk key stops unsealing. Always seal to the narrowest necessary PCR set and keep a recovery path.
  • TPM bus sniffing. A discrete TPM talks to the CPU over LPC or SPI in the clear. Unsealed keys have been recovered with a logic analyser and physical access. Firmware TPMs and parameter encryption mitigate this.
  • Emulated ≠ attested. Cuttlefish's secure_env is excellent for functional testing and useless as a security boundary — the host owns the TPM state. Never validate an anti-tamper control solely on a virtual device.
  • Rollback without fuses. If the rollback index lives in software-writable storage, downgrade protection is decorative.
  • The HSM will sign whatever you ask. It protects the key, not the authorisation logic in front of it. Most real HSM incidents are credential or quorum failures, not cryptographic ones.
60-second recapHardware-backed trust closes the loop
  • Verified boot enforces approved software; measured boot records exactly what loaded.
  • Rollback indexes add freshness so an older but validly signed image can still be rejected.
  • TPMs, TEEs, StrongBox and HSMs protect keys differently and do not validate application intent.
Explain it to a colleagueHardware trust matters because software cannot reliably keep a secret from a machine that fully controls it. The hardware boundary can refuse extraction and bind operations to measured state.
Knowledge check 06

Malware gains kernel execution after the boot chain has completed. Why can it not rewrite PCR values to hide the components that were measured?

PCRs are stored in write-once fuses
PCRs support only extend — PCR = H(PCR ‖ new) — so any additional write produces a different value rather than a chosen one
The TPM requires a password to modify PCRs, held only by the bootloader
It can, which is why measured boot is considered obsolete

Extend-only is the core property. Reaching a specific target value would require inverting SHA-256. The register resets only on reboot, which restarts the chain from a known state.

You ship a KeyMint-attested key from a Cuttlefish instance to your backend, which checks the chain against Google's hardware attestation root. What should the backend conclude?

The key is in tamper-resistant hardware; treat it as StrongBox-equivalent
The chain will validate normally, so the device is genuine
Cuttlefish uses test attestation keys that do not chain to the production Google root, and its security level is TRUSTED_ENVIRONMENT with device-unique attestation refused
Attestation is unavailable on virtual devices

Attestation works functionally on Cuttlefish — which is what makes it a good test target — but it is backed by a host software TPM and test keys. It exercises your parsing and policy code; it cannot substantiate a hardware claim.

A signed OTA fixes a critical vulnerability, but the rollback index is left unchanged. What attack remains?

Flashing the previous, still-validly-signed build to reintroduce the vulnerability
Forging a new vbmeta signature
Extracting the AVB private key from the device
None; the signature check is sufficient

Signature verification answers "was this authentic?" not "is this current?" Without a rollback index increment stored in tamper-evident storage, the old signed image is indistinguishable from the new one to the bootloader.
