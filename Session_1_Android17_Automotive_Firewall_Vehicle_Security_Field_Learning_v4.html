2. The simplest useful mental model

Analogy: a secured office campus

UID = employee badge. Android does not primarily ask “Which app name sent this?” It asks “Which Linux UID owns the socket?”

Framework policy = security desk. User settings and system state become rules: background blocked, VPN required, UID allowed, UID denied.

TrafficController/eBPF = electronic gate. The rule is installed once; packets are checked quickly in the kernel.

The critical distinction

netd is not a toll booth that every packet visits. It configures routes, interfaces and firewall/BPF state. Once configured, normal packets move through the kernel data path.

This explains why Android can enforce per-app networking without sending every packet into a slow userspace daemon.

4. AOSP networking components

App/framework APIs

ConnectivityManager, NetworkRequest and NetworkCapabilities let apps observe or request networks. Apps do not directly edit system routes or firewall maps.

ConnectivityService

The central framework connectivity service tracks networks, default-network selection, requests, capabilities and routing decisions at the Android framework level.

Network Stack module

An updatable Mainline module for functions such as IP provisioning, captive portal behavior and packet-filter improvements. “Network Stack” is not a synonym for all Android networking.

NetworkPolicyManagerService

Turns user and system policy—such as Data Saver and per-UID metered rules—into enforceable UID rules.

NetworkStatsService

Reads and persists traffic accounting. It consumes UID, tag and interface statistics gathered through the kernel/eBPF infrastructure.

netd

A privileged native daemon/service used by the framework for network configuration tasks. It coordinates lower-level routing, interface, firewall and resolver-related operations.

TrafficController

Manages eBPF maps and per-UID owner/firewall state, socket tagging and traffic statistics integration.

bpfloader

Loads precompiled Android eBPF programs during boot and attaches them to the appropriate kernel hooks.

Linux kernel

The actual packet data plane: sockets, UID ownership, cgroups, eBPF hooks/maps, routing, netfilter, TUN/TAP and device drivers.

5. netd and TrafficController

🎯 Mission 2 — Enter the control room

Discover who decides policy, who installs it, and why packets do not visit netd one by one.

12 minutesReward: control-plane insight

netd: privileged configuration worker

Framework services communicate with netd through privileged interfaces. netd applies system-level network configuration that ordinary applications cannot perform.

  • Interface and route configuration
  • Firewall and UID-related operations
  • Network creation and permission coordination
  • Integration with lower-level networking services

TrafficController: UID-aware BPF manager

TrafficController connects Android policy with eBPF maps/programs. It manages data used for socket tagging, traffic statistics and per-UID filtering.

  • UID owner/firewall rule state
  • Socket tag and counter-set state
  • UID, interface and tag accounting maps
  • Map updates consumed by kernel programs
Control-plane story: NetworkPolicyManagerService decides “UID 10123 is restricted.” TrafficController updates a BPF map. The kernel program later checks that map when traffic from the UID reaches its hook.

Myth: netd proxies every app connection. False.

Myth: iptables alone is the modern Android per-UID firewall. False. Modern Android relies heavily on eBPF-based UID accounting/filtering, while netfilter hooks still have roles.

Myth: TrafficController is the same thing as Linux tc. False. The names are similar; their purposes are different.

🧠 Remember this forever — control plane
  1. Framework policy decides what should happen.
  2. netd / TrafficController apply privileged network configuration and BPF state.
  3. The kernel later enforces that installed state on traffic.

6. Android UID model

🎯 Mission 1 — Earn the identity badge

Calculate PKT-10123’s full UID and explain why the kernel trusts a numeric UID more than a package label.

10 minutesBadge: UID Detective

Why UID is the firewall identity

Android assigns a Linux UID to each application sandbox. The kernel can reliably associate a socket with its owner UID, even if the app uses native code or several processes.

Package name is for humans; UID is for enforcement. Package-to-UID mapping can be inspected, but the kernel checks numeric identity.

Multi-user UID formula

Android allocates a range of 100,000 UIDs per Android user/profile:

uid = userId × 100000 + appId

A personal-profile app and the same package in a work profile have different full UIDs.

UID calculator

User 0 + appId 10123 → UID 10123

One app, several processes

Processes normally remain inside the same app sandbox and share the application UID, so their sockets receive the same per-app network policy.

System UIDs

Android services and native daemons also run under defined system identities. A firewall decision can therefore distinguish ordinary apps from privileged services.

Isolated identities

Android can create isolated processes with separate UIDs for stronger containment. Do not assume every process belonging to an app always exposes the app’s base UID.

🧠 Remember this forever — UID identity
  1. Package name is a human-friendly label; numeric UID is the kernel-relevant identity.
  2. Android users/profiles change the full UID.
  3. Always map the failing package/process to its actual UID before reasoning about per-app network policy.

8. BPF UID filtering

🎯 Mission 3 — Pass the kernel gate

Separate executable BPF logic from mutable map state, then process an allow and a drop event.

15 minutesBadge: BPF Explorer

What eBPF means here

eBPF programs are verified kernel programs attached to specific hooks. Android loads approved programs at boot; ordinary apps do not upload arbitrary firewall code.

A cgroup socket/transport hook can identify the socket UID, consult maps and count or block traffic. Netfilter’s xt_bpf integration can also support interface accounting at packet hooks.

Programs versus maps

Program: the decision logic—like a small gatekeeper.

Map: shared key/value state—UID rules, counters, tags and configuration.

TrafficController changes map entries without recompiling the kernel program.

Explain eBPF at your level

9. Data Saver, VPN and restricted networking

Data Saver

User-controlled policy for reducing usage on metered networks. Ordinary background data is blocked for affected UIDs unless allowlisted. Foreground use is generally permitted, while apps are encouraged to reduce usage.

VPN

VpnService establishes a local TUN interface. Android routes selected app traffic into that interface; the VPN app reads packets, encrypts them and sends them to the gateway.

Restricted network

A network without NET_CAPABILITY_NOT_RESTRICTED is not for general app use. Access requires privileged authorization such as OEM-controlled CONNECTIVITY_USE_RESTRICTED_NETWORKS.

Data Saver truth table

Data Saver off → no Data Saver block.

VPN path simulator

Select a scenario.

Always-on and lockdown

Always-on asks Android to keep the VPN service active. “Block connections without VPN” prevents eligible traffic from escaping through an ordinary network while the protected VPN path is unavailable.

Per-app VPN

A VPN can use an allowed list or disallowed list, but not both for the same interface. Apps outside the selected set follow the applicable non-VPN policy.

🧠 Remember this forever — policy families
  1. Data Saver is mainly about affected background traffic on metered networks.
  2. VPN lockdown is about preventing non-VPN escape when the required VPN path is unavailable.
  3. Restricted-network eligibility and Android 17 local-network permission are separate questions.

10. AAOS: what changes when Android lives in a vehicle?

Android Automotive OS uses the Android platform and security model, then extends it for in-vehicle requirements. Keep the Android networking foundation—but add automotive connectivity, vehicle integration and vehicle-domain boundaries.

Standard Android foundation

App UID sandbox, ConnectivityService, NetworkPolicyManager, netd, TrafficController, eBPF, routes, VPN and network capabilities.

AAOS-specific additions

PANS, OEM network preferences, OEM_PAID/OEM_PRIVATE capabilities, Car framework/services and VHAL integration.

OEM / vehicle architecture

Actual vehicle buses, gateways, domain controllers, Ethernet segmentation, ECU authorization and IDS/IPS are OEM-specific and are not replaced by Android UID filtering.

11. PANS — Per-Application Network Selection

PANS is an automotive-only connectivity feature that lets an OEM map applications to OEM network preferences without requiring ordinary app code changes.

Why a vehicle needs it

A vehicle can have several simultaneous networks with different owners, costs and purposes: user Wi-Fi, user-paid cellular, OEM-paid data and OEM-private connectivity. PANS lets the platform give selected applications an appropriate default network.

Important nuance

OEM_PAID and OEM_PRIVATE networks are restricted. Apps explicitly requesting restricted networks normally require privileged authorization, but apps mapped by PANS can receive the mapped restricted OEM network as their default without separately holding the restricted-network permission for that default use.

13. Vehicle trust boundaries — where Android networking stops

A secure vehicle architecture treats the IVI/AAOS environment as one domain inside a larger vehicle. A compromise of an Android app must not automatically become access to safety-relevant ECUs.

1. App sandbox

UID, SELinux, permissions, Android networking policy.

Protects apps from each other and limits platform operations.

2. AAOS / IVI

PANS, restricted networks, Car APIs, system services.

Controls app network selection and access to vehicle-facing APIs.

3. Vehicle gateway/domain

OEM-specific network segmentation, service filtering and authorization.

Separates infotainment from other vehicle networks/domains.

4. ECU / safety domain

ECU-local controls, authenticated services, diagnostics policy and safety mechanisms.

Must not trust “Android firewall passed” as sufficient authorization.

Boundary reasoning simulator

Choose an actor and target. This is an architecture reasoning tool, not a universal OEM ACL.
Never teach this shortcut: “eBPF blocked the app, therefore the vehicle network is protected.” Android UID/eBPF enforcement is one layer. Vehicle-domain segmentation and ECU/gateway authorization are separate layers with separate failure modes.

🛡 Vehicle boundary

IVI reachability toward a safety-relevant ECU is a gateway/domain-security problem. Android UID filtering and PANS are necessary layers, not complete vehicle authorization.

🧯 Troubleshooting order

  1. Confirm Android/AAOS baseline.
  2. Identify package UID.
  3. Check capabilities and selected/default network.
  4. For automotive routing, check PANS and OEM network availability.
  5. Check Data Saver, UID policy, VPN and routes.
  6. If vehicle property data fails, move to CarService/VHAL.
  7. If traffic crosses from IVI toward another vehicle domain, inspect gateway/domain/ECU authorization.

restore_data_saver() {

  fail "API level: $SDK"

[[ "$TYPE" == 'userdebug' ]] &&

[[ "$BOOT" == '1' ]] &&

[[ "$SELINUX" == 'Enforcing' ]] &&

26. Android 17 / AAOS notes relevant to vehicle firewall training

Local-network access is a separate permission question

For apps targeting API 37, broad LAN access can require ACCESS_LOCAL_NETWORK. A socket error caused by missing local-network permission is not automatically a netd/BPF firewall defect.

Target SDK matters

An Android 17 device can run an app targeting an older SDK with compatibility behavior. Always record both the platform API and the app’s targetSdk when troubleshooting.

PACKAGE='com.example.firewalllab'

"$ADB" -s "$SERIAL" \
  shell dumpsys package "$PACKAGE" |
  grep -E \
  'targetSdk|versionCode|versionName|ACCESS_LOCAL_NETWORK'
Troubleshooting discipline: identify the layer that rejected the operation—app permission, framework policy, PANS/default-network selection, VPN, UID firewall, route, DNS, CarService/VHAL, vehicle gateway or remote endpoint—before changing rules.
Release naming: this training lab uses the Android 17/API 37 baseline already validated in your Cuttlefish environment. AAOS platform releases can be delivered on automotive release trains; do not assume a generic Android Cuttlefish image automatically includes the AAOS CarService/PANS/VHAL stack.

29. Tap-to-flip glossary

UID
Linux numeric identity used to isolate an app and attribute its sockets and traffic.
netd
Privileged Android native networking service used to apply system network configuration.
TrafficController
Android component managing BPF-based UID rules, tagging and traffic statistics state.
eBPF program
Verified logic running at a specific kernel hook.
BPF map
Kernel-accessible key/value storage shared with userspace control components.
TUN
Virtual layer-3 interface that exchanges IP packets with a userspace VPN service.
Metered network
A network Android treats as potentially costly or data-limited.
Restricted network
A network not available for general app use without privileged authorization.
Control plane
Components that decide and install rules, routes and policy.
PANS
Per-Application Network Selection: automotive-only policy for mapping apps to OEM network preferences.
OEM_PAID
Restricted OEM network capability commonly used for OEM-funded app traffic with defined fallback preferences.
OEM_PRIVATE
Restricted OEM network capability intended for dedicated OEM connectivity rather than general app use.
VHAL
Vehicle Hardware Abstraction Layer: property-based interface between Android automotive services and vehicle-specific hardware integration.
Vehicle trust boundary
A boundary where authorization and isolation must be enforced between IVI/AAOS and other vehicle networks or domains.
