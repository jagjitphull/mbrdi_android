Where AI actually lives in a vehicle

Artificial intelligence in a vehicle is not one “AI box.” It is a collection of models and decision logic embedded across sensing, driver interaction, vehicle control support, diagnostics, cybersecurity, cloud services and development pipelines.

👁️
Perception

Camera, radar and LiDAR models detect lanes, objects, signs, free space and driver state.

Real world: ADAS object detection, parking, driver monitoring.
🧭
Prediction & planning

Models estimate motion or intent and help choose a safe trajectory or assistance action.

Real world: adaptive cruise, automated lane changes, ADS.
🎙️
In-cabin assistants

Speech/LLM systems answer questions, control non-safety functions, retrieve cloud content and personalize experiences.

Real world: navigation, media, HVAC, service support.
🩺

Models spot unusual thermal, battery, motor, vibration or fault patterns.

Real world: fleet health and warranty analytics.
🛡️

Anomaly models can score CAN, Ethernet/SOME-IP, backend or ECU telemetry.

Real world: vehicle IDS and fleet VSOC prioritization.
☁️

Real world: continuous improvement and model OTA.

🧬 Mission 03

Attack taxonomy: the language engineers need

+25 XP

NIST’s 2025 adversarial-ML taxonomy groups AI attacks by lifecycle stage, attacker goals, capabilities and knowledge. In automotive work, translate that into asset → manipulation → AI effect → vehicle effect → evidence → treatment.

INTEGRITY

Evasion

Craft or manipulate inference-time input so a trained model produces an undesirable output.

  • Camera perturbation / deceptive visual cue
  • Feature manipulation in telemetry
  • Detection threshold exploitation
INTEGRITY

Poisoning

Corrupt training, fine-tuning, feedback, labels or data-selection processes so future model behavior is degraded or attacker-influenced.

STEALTH

Backdoor / Trojan

Model behaves normally for ordinary inputs but changes behavior when a trigger pattern is present.

CONFIDENTIALITY

Privacy / extraction

Infer training membership, sensitive attributes, model parameters or a useful imitation through queries or artifact access.

GENAI

Prompt / context abuse

Injected or adversarial content attempts to override system policy, manipulate retrieval or induce unsafe tool calls.

AVAILABILITY

Resource / confidence attacks

Inputs cause excessive compute, unstable confidence, repeated fallback, alert overload or degraded service.

Knowledge model

Attacker knowledgeMeaningAutomotive interpretation
White-boxDetailed knowledge of model/parameters/gradients.Compromised dev environment, leaked model or insider access.
Gray-boxPartial architecture, data or interface knowledge.Supplier docs, API behavior, firmware observations.
Black-boxMostly query/response behavior.Externally observable service, assistant or repeated sensor interaction.

What defenders measure

📡 Mission 05

Sensor spoofing & fusion security

+40 XP
📖 Teach me🎬 Show me🧪 Let me try🎯 Test me

Sensor spoofing manipulates a physical or digital measurement source—GPS/GNSS, radar, LiDAR, ultrasonic, camera or inertial data—so downstream AI receives believable but false evidence. The strongest defense is often independent corroboration, not blind trust in a single sensor.

GNSS

Check inertial/odometry consistency, impossible jumps, time anomalies and map plausibility.

Radar/LiDAR

Use tracking continuity, cross-modal object confirmation, physics constraints and health diagnostics.

Ultrasonic/camera

Correlate with vehicle motion, neighboring sensors, exposure/occlusion health and scene context.

Poisoning targets the learning process. The attacker may alter examples, labels, feedback, synthetic data, data selection, pre-trained weights or fine-tuning artifacts. A backdoor is especially dangerous because ordinary validation can look healthy while a rare trigger causes attacker-chosen behavior.

☠️ The Poisoner vs 🚪 The Hidden Door
Poisoning changes learning. A backdoor is the stealthier outcome: normal accuracy can stay healthy while one trigger path becomes dangerous.

Controls before training

  • Immutable dataset versions and cryptographic hashes
  • Source identity and lineage
  • Label QA with disagreement sampling
  • Outlier / duplicate / cluster analysis
  • Supplier artifact verification and SBOM-style provenance

Controls after training

  • Holdout sets from independent sources
  • Trigger-oriented red-team evaluation
  • Behavior comparison to prior signed model
  • Canary/shadow deployment and rollback
  • Model registry approval gates

🕵️ Mission 09

AI-based CAN / SOME-IP IDS evasion

+45 XP

Vehicle anomaly detection can learn message frequency, payload patterns, state transitions and cross-signal relationships. An attacker may try to remain near the learned baseline, slowly drift a value, mimic legitimate timing, poison the baseline, or create alert noise.

Weak detector

“Alert if CAN ID 0x123 exceeds 100 frames/s.”

Easy to stay below one threshold.

Stronger detector

Correlates rate + payload semantics + vehicle state + ECU identity + transition rules.

Operational detector

Combines on-vehicle low-latency controls with fleet analytics and incident context.

False positives matter. A detector that screams during every legitimate software update, diagnostic session or driving-state transition trains operators to ignore it. Security engineering includes baselining, explainability and response playbooks.

Models are software artifacts with extra baggage: training provenance, dataset versions, preprocessing code, dependencies, evaluation evidence, hardware assumptions and runtime thresholds. An update is trustworthy only when both artifact integrity and deployment intent are verified.

Threats

  • Compromised CI runner or registry
  • Unsigned/re-signed malicious model
  • Stolen signing key
  • Dependency or preprocessing compromise
  • Rollback to vulnerable model
  • Wrong model/hardware/configuration pairing

Controls

  • Separate build, approval and signing roles
  • Hardware-backed key protection where appropriate
  • Artifact hash + signature + version policy

  • Known-good rollback and anti-rollback policy
Regulatory bridge: UNECE R156 addresses software-update management and includes integrity/authenticity and safe update execution concepts. AI model updates should be engineered within that broader software-update governance rather than treated as an informal “data science deploy.”
🏰 Mission 11

Production defensive architecture: assume one layer will fail

+50 XP
📖 Teach me🎬 Show me🧪 Let me try🎯 Test me

Five non-negotiable design principles

  1. Safety-critical action must not depend on raw LLM output.
  2. One sensor or model should not be a single point of unsafe trust.
  3. Model identity and configuration are verified artifacts.
  4. AI decisions need observable context: model version, confidence, input health, fallback state and decision reason.
  5. Fallback is a security feature. Define what the vehicle does when AI trust collapses.

TARA & compliance mapping for AI threats

+55 XP

ISO/SAE 21434 provides lifecycle cybersecurity engineering and risk-management requirements for road-vehicle E/E systems. UNECE R155 establishes cybersecurity/CSMS requirements for applicable vehicle type approval regimes. Neither should be reduced to a checklist of “AI controls”: AI threats belong in the same asset, threat-scenario, risk-treatment and evidence lifecycle.

Lab 1 — Detect synthetic sensor disagreement

Goal: reject a spoofed position measurement when it disagrees with independent odometry.

cat > ~/ai-vehicle-lab/sensor_fusion_guard.py <<'PY'
import math
samples = [
    {"t":1,"gnss":100.0,"odo":100.4},
    {"t":2,"gnss":101.2,"odo":101.4},
    {"t":3,"gnss":129.0,"odo":102.5}, # synthetic spoof
    {"t":4,"gnss":103.6,"odo":103.5},
]
LIMIT_METERS = 5.0
for s in samples:
    delta = abs(s["gnss"] - s["odo"])
    verdict = "REJECT_GNSS" if delta > LIMIT_METERS else "ACCEPT"
    print(f't={s["t"]} delta={delta:.1f}m verdict={verdict}')
PY
python ~/ai-vehicle-lab/sensor_fusion_guard.py
Acceptance: t=3 prints REJECT_GNSS; other samples print ACCEPT. Explain why the threshold must be calibrated to operating context rather than copied blindly.

Lab 5 — Sign, verify and tamper with a model artifact

cd ~/ai-vehicle-lab
printf 'toy-model-version=1\nthreshold=0.72\n' > model.bin
openssl genpkey -algorithm ED25519 -out model-signing-key.pem
openssl pkey -in model-signing-key.pem -pubout -out model-signing-pub.pem
openssl pkeyutl -sign -inkey model-signing-key.pem -rawin -in model.bin -out model.sig
openssl pkeyutl -verify -pubin -inkey model-signing-pub.pem -rawin -in model.bin -sigfile model.sig

# Controlled tamper
printf 'threshold=0.10\n' >> model.bin
openssl pkeyutl -verify -pubin -inkey model-signing-pub.pem -rawin -in model.bin -sigfile model.sig || echo 'EXPECTED: verification failed'
Acceptance: first verification succeeds; verification after tampering fails. Explain why production signing keys should not sit beside artifacts on a normal build host.

Lab 6 — Deterministic tool gate for a mock vehicle assistant

cat > ~/ai-vehicle-lab/tool_gate.py <<'PY'
ALLOWED = {'set_cabin_temp', 'play_media', 'get_navigation_eta'}
DENIED_SAFETY = {'disable_brakes','steer_vehicle','disable_security_logging'}

def authorize(tool, user_confirmed=False):
    if tool in DENIED_SAFETY:
        return False, 'safety/security domain is not exposed to assistant'
    if tool not in ALLOWED:
        return False, 'tool not allowlisted'
    if tool == 'set_cabin_temp' and not user_confirmed:
        return False, 'confirmation required by policy'
    return True, 'allowed'

for tool in ['play_media','disable_security_logging','unknown_tool']:
    print(tool, authorize(tool, user_confirmed=True))
PY
python ~/ai-vehicle-lab/tool_gate.py
Acceptance: media is allowed; security logging and unknown tool are denied. Trainee explains why an LLM’s textual “decision” must not be the authorization mechanism.

Fast glossary

+20 XP
Adversarial example

An input intentionally manipulated to cause an undesirable model output while often remaining plausible to a human or system.

Backdoor / Trojan

Hidden behavior activated by a trigger while normal inputs may continue to perform well.

Data poisoning

Manipulation of training/fine-tuning/feedback data or labels to degrade or influence the learned model.

Distribution shift

Operational input differs from the data distribution the model was developed or validated against. It may be natural rather than malicious.

OOD — out of distribution

Input that differs materially from the learned/validated domain.

Sensor fusion

Combining multiple sensing sources to improve state estimation and reduce dependence on one source.

Model drift

Model performance or data relationships change over time.

Prompt injection

Untrusted instructions or content attempt to manipulate a generative AI system’s intended behavior or tool use.

Model extraction

Attempts to recover model information or approximate its behavior via access or queries.

Canary deployment

Release to a limited cohort first so health can be observed before broader rollout.

Attestation

Evidence about software/platform identity or state used to decide whether it should be trusted.

Safety envelope

Rules/constraints that prevent an AI output from directly causing behavior outside defined safe bounds.
