01 • Mental model

TLS protects a conversation, not the whole system

A secure TLS session gives the endpoints cryptographic properties. It does not guarantee the application is safe, the endpoint is uncompromised, the certificate name is correct, or the traffic pattern is private.

🔐

Confidentiality

Application bytes are encrypted so passive observers cannot directly read them.

🧾

Authentication

Usually the server proves identity with a certificate and signature. Client authentication is optional unless mTLS is used.

🧬

Integrity

Changes to protected records are detected cryptographically.

👁

Metadata remains

IP addresses, timing, sizes and often other connection metadata can remain observable.

Side-channel idea: secrets can leak through something other than the mathematical output — timing, cache behavior, branch behavior, power, packet size, compression length or error behavior.
02 • Compare

TLS 1.2 vs TLS 1.3: what actually changed?

TLS 1.2

  • Many historical cipher-suite combinations.
  • Could use RSA key transport in legacy deployments, which does not provide forward secrecy.
  • CBC suites existed alongside AEAD suites.
  • Handshake is largely visible until ChangeCipherSpec/Finished.
  • Master-secret derivation uses the TLS 1.2 PRF.
  • Two-round-trip full handshake in the common case.

TLS 1.3

  • Removes static RSA/DH key exchange and legacy CBC/RC4 cipher suites.
  • Standard cipher suites are AEAD-based.
  • Ephemeral (EC)DHE is used for ordinary certificate-based handshakes, giving forward secrecy.
  • Most handshake messages after ServerHello are encrypted.
  • HKDF-based key schedule with distinct handshake/application secrets.
  • One-round-trip full handshake; PSK resumption can enable 0‑RTT early data.

04 • Crypto internals

Key derivation without the fog

TLS 1.2 — PRF mental model

premaster secret+ClientRandom+ServerRandom→ PRF →master secret

The master secret feeds a key expansion process that derives record-protection material. Exact outputs depend on the negotiated suite.

Important: if old RSA key transport was used and the server’s RSA private key is later stolen, recorded sessions could be decrypted. Ephemeral ECDHE avoids that property.

TLS 1.3 — HKDF tree

PSK / zeros→Early Secret→Handshake Secret→Master Secret

HKDF-Extract and HKDF-Expand-Label derive separate client/server handshake traffic secrets, application traffic secrets, Finished keys, exporter secrets and resumption material.

05 • Record layer

CBC’s sharp edges vs AEAD’s cleaner contract

Historical CBC-style protection

plaintext → MAC → padding → CBC encryption

Different error paths, padding validity, MAC checking and variable-time work created fertile ground for padding/timing oracles when implementations leaked distinctions.

Attacker question: “Can I learn one bit from how the endpoint reacts to malformed ciphertext?” Repeat that observation enough times and tiny leaks can become large ones.

AEAD protection

plaintext + associated data + nonce → ciphertext + authentication tag

TLS 1.3 standardizes AEAD suites such as AES-GCM and ChaCha20-Poly1305. This removes the TLS CBC padding/MAC design that powered attacks such as Lucky13.

Still not magic: AEAD does not eliminate implementation side channels, nonce misuse in other protocols, endpoint compromise, traffic analysis or application-layer compression leaks.

This simulator deliberately exaggerates timing differences so the mechanism is visible. Real cryptographic side channels may require careful statistics, colocated execution, microarchitectural knowledge, many observations, or specific vulnerable implementations.

How leakage compounds

One sample is noisy. Thousands of correlated samples can reveal structure.

Defensive coding principles

  • Use vetted crypto libraries and constant-time primitives.
  • Avoid secret-dependent branches and memory access where applicable.
  • Keep protocol errors indistinguishable when the design requires it.
  • Patch cryptographic libraries and microcode; track implementation advisories.
  • Separate secrets from hostile colocated workloads when the threat model warrants it.
09 • TLS 1.3 special case

0‑RTT trades latency for replay complexity

Normal resumption

  1. Client previously received a resumption PSK/ticket.
  2. Client reconnects and proves possession.
  3. Application data waits until handshake progress provides the intended replay properties.

0‑RTT early data

  1. Client derives an early traffic secret from the PSK.
  2. Client can send early application bytes immediately.
  3. Those bytes do not have the same replay protection guarantees as ordinary 1‑RTT application data.

Replay animation

Client ── early data ──▶ Server\n Action executes once.
Application rule: do not put replay-sensitive state changes — money movement, irreversible commands, one-time authorization — into 0‑RTT unless the application has a robust anti-replay design.
10 • Beyond ciphertext

What Eve can still learn

Switch transport/privacy modes and watch which observations remain available to a passive network observer. “Protected” means the selected mechanism is designed to hide that item from this observer model — not that the whole system becomes anonymous.

Traffic shape

Lengths, direction and timing can remain useful signals even when payloads are encrypted.

Handshake fingerprint

ClientHello structure can fingerprint software families and policy. Treat fingerprinting as probabilistic classification, not identity proof.

ECH

ECH protects the sensitive inner ClientHello, including the true server name, when the client-facing service and discovery path support it. IP/traffic metadata can still remain.

11 • Defensive architecture

Defence in layers

Protocol floor

Prefer TLS 1.3. Where TLS 1.2 is required, restrict it to modern AEAD + forward-secret configurations. Disable SSLv2/3 and TLS 1.0/1.1.

PKI correctness

Verify chain, hostname/SAN, validity, trust anchors and application-specific identity requirements. Never “fix” certificate errors by disabling verification.

Implementation safety

Patch OpenSSL/crypto libraries, use constant-time primitives, avoid home-grown crypto, and monitor side-channel advisories relevant to your CPU/workload model.

Application safety

Disable TLS compression, treat BREACH-like application compression separately, use CSRF defenses and avoid reflecting secrets into attacker-controlled compressed responses.

0‑RTT policy

Default off for replay-sensitive endpoints. If enabled, restrict to safe/idempotent operations and implement anti-replay at the architecture layer.

Observability

Track protocol/cipher negotiation, certificate expiry, client failures, downgrade anomalies and unexpected legacy protocol use — without logging secrets.

11A2 • Protocol bridge

Where TLS sits with HTTP/1.1, HTTP/2 and HTTP/3

The phrase “HTTPS” hides two different transport architectures. HTTP/1.1 and HTTP/2 commonly run over TLS over TCP. HTTP/3 runs over QUIC over UDP, with the TLS 1.3 handshake integrated into QUIC rather than carried as ordinary TLS records over TCP.

11D • Production patterns

Small, auditable TLS configuration recipes

These recipes emphasize protocol floors and certificate handling, not giant copied cipher strings. Always test against your exact server/library versions and compatibility requirements.

server { listen 443 ssl; server_name example.test; ssl_certificate /etc/tls/fullchain.pem; ssl_certificate_key /etc/tls/private.key; ssl_protocols TLSv1.2 TLSv1.3; }

Nginx currently documents TLSv1.2 and TLSv1.3 as the default protocol set in the HTTP SSL module; explicit configuration can make policy intent easier to audit.

<VirtualHost *:443> SSLEngine on SSLCertificateFile /etc/tls/fullchain.pem SSLCertificateKeyFile /etc/tls/private.key SSLProtocol -all +TLSv1.2 +TLSv1.3 </VirtualHost>

Apache mod_ssl delegates cryptography to the linked SSL/TLS library; validate supported protocol syntax on the installed build.

global ssl-default-bind-options ssl-min-ver TLSv1.2 frontend https_in bind :443 ssl crt /etc/haproxy/certs/site.pem default_backend app

HAProxy documents ssl-min-ver as a way to enforce a minimum protocol version globally or on bind lines.

openssl s_server -accept 9444 \ -cert server.crt -key server.key \ -tls1_3 -www

Use OpenSSL test endpoints for controlled labs and diagnosis — not as a production web server.

Lab 1 — Build a local certificate identityLOCAL / SAFE

Create an isolated working directory and a self-signed certificate for localhost.

Lab 6 — Certificate validation failure is a featureLOCAL / SAFE

With the Lab 3 server running, omit the trust anchor:

openssl s_client -connect 127.0.0.1:9444 -tls1_3 \ -verify_return_error -brief </dev/null
Checkpoint: verification fails because the self-signed lab certificate is not in the default trust store. Re-run with -CAfile ~/tls-lab/server.crt and verification succeeds.

Lab 9 — Safe timing side-channel statisticsSYNTHETIC

This intentionally vulnerable toy compares bytes and sleeps longer for each correct prefix. It uses a fake secret and loopback-only logic so learners can see why early-exit comparison leaks timing.

cat > ~/tls-lab/timing_demo.py <<'PY' import time, statistics, random SECRET=b'LAB-42' def leaky(candidate): start=time.perf_counter_ns() for a,b in zip(candidate,SECRET): if a != b: break time.sleep(0.0005) time.sleep(random.random()*0.00015) return time.perf_counter_ns()-start for guess in [b'X',b'L',b'LA',b'LAB',b'LAB-4',b'LAB-42']: samples=[leaky(guess) for _ in range(30)] print(guess, round(statistics.mean(samples)/1e6,3),'ms') PY python3 ~/tls-lab/timing_demo.py
Checkpoint: guesses sharing longer correct prefixes trend slower. Defence: do not implement secret comparison this way; use vetted constant-time facilities appropriate to the language/library.
Lab 10 — Compression-length oracle mental modelSYNTHETIC

This is a safe miniature of the information principle behind compression attacks: repeated attacker-controlled text can compress better when it matches nearby secret text.

cat > ~/tls-lab/compress_demo.py <<'PY' import zlib secret='TOKEN=ORANGE-CAR' def size(attacker): body=f'header={secret}&guess={attacker}&again={attacker}' return len(zlib.compress(body.encode())) for g in ['TOKEN=X','TOKEN=O','TOKEN=OR','TOKEN=ORA','TOKEN=ORANGE-CAR']: print(f'{g:18} compressed_bytes={size(g)}') PY python3 ~/tls-lab/compress_demo.py
Checkpoint: compressed length can depend on similarity between attacker input and secret-bearing content. TLS encryption does not hide ciphertext length. Real BREACH mitigations therefore live partly at the HTTP/application-compression layer.
Lab 11 — Certificate hostname verificationLOCAL / SAFE

With the localhost TLS server running, prove that identity checking is name-specific.

openssl s_client -connect 127.0.0.1:9444 -tls1_3 \ -CAfile ~/tls-lab/server.crt -verify_hostname localhost \ -verify_return_error -brief </dev/null # Intentional mismatch — expected to fail verification openssl s_client -connect 127.0.0.1:9444 -tls1_3 \ -CAfile ~/tls-lab/server.crt -verify_hostname wrong.example \ -verify_return_error -brief </dev/null
Checkpoint: localhost verifies; the wrong hostname fails. Trusting the issuer is not enough — the intended server identity must also match.

What a PASS means

A PASS proves the local mechanism worked on that machine. It does not prove your production endpoint is hardened. Production validation additionally needs policy review, externally observable protocol testing, certificate lifecycle checks and application-specific 0‑RTT/compression review.

15 • Incident missions

Think like the engineer on call

Mission A — “TLS 1.3 is enabled, so we are safe.”

A login response includes a CSRF token and reflects attacker-controlled data in the same compressed HTTP response.

Reveal analysis

TLS 1.3 removes historical TLS-level compression/CBC weaknesses, but an application-layer compression-length leak can still matter. Review secret placement, compression policy and anti-CSRF design.

Mission B — “Certificate error? Use -k.”

A service broke after certificate rotation and an operator proposes disabling verification.

Reveal analysis

Find the identity/trust failure: wrong SAN, incomplete chain, expired cert, wrong trust anchor, clock error or proxy interception. Disabling verification removes server-authentication assurance.

Mission C — “0‑RTT makes checkout faster.”

A POST endpoint changes state and is proposed for early data.

Reveal analysis

Replay risk is an application property. Keep replay-sensitive operations out of 0‑RTT unless a robust anti-replay/idempotency architecture exists.
