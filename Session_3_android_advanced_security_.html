2. Isolation is a ladder, not one wall

Click through the layers. Stronger boundaries usually cost more memory, startup time, integration effort and communication complexity.

Permission/APIWho may request an operation?
UID + SELinuxWhich process may access which object?
NamespaceWhich kernel objects are visible?
cgroup + BPFHow much resource and what programmable policy?
Isolated processSeparate UID with no app permissions of its own
pVM / separate ECUSeparate kernel or hardware trust domain
Start with the least expensive boundary that satisfies the threat model. Add layers rather than replacing all lower layers.

Security isolation

UIDs, SELinux, seccomp, namespaces and pKVM restrict access and reduce blast radius.

Resource isolation

cgroups control CPU, memory, process count, freezer state and scheduling placement. They are not a confidentiality boundary by themselves.

Routing isolation

PANS, UID routing, VPNs and restricted network capabilities control which network path an app receives. They do not create a separate kernel.

3. PANS and per-application network selection

What PANS solves

Per-application network selection maps an automotive app package to an OEM network preference. It lets an OEM pay for selected critical traffic while ordinary consumer traffic uses the user's/default network.

The automotive-only ConnectivityManager.setOemNetworkPreference() System API maps package names to one preference each.

What PANS does not do

PANS changes an app's default network. A specialized request—such as an app explicitly asking for an unmetered network—can still apply. PANS is not an app VPN and not a separate network namespace.

Preferences are not persisted across boot and must be reapplied.

Automotive example: map navigation and hands-free assistant to OEM-paid connectivity, map diagnostics to OEM-private connectivity, and leave streaming media on the user's normal data plan.

4. Android network namespaces

Linux concept

A network namespace owns its own interface list, routes, neighbor tables, firewall state and socket namespace. Two processes in different netns can both have an interface named eth0 but see different networks.

Android reality

AOSP does not normally create one network namespace per app. Ordinary app traffic is separated mainly through socket UID, SELinux, UID routing, VPN policy and BPF/firewall rules. Verify your build by comparing /proc/PID/ns/net inode links.

Controls process-ID visibility. Do not assume a normal Android app gets its own PID namespace.

An Android dynamic-linker namespace controls which native libraries are visible. It is unrelated to Linux network namespaces despite sharing the word “namespace.”

5. cgroup v2 and BPF

cgroups: organize and control tasks

cgroups group processes/threads hierarchically for resource accounting and control. Android supports cgroup v1 and v2 and uses a task-profile abstraction so framework code does not hard-code filesystem paths.

cgroups.json describes controllers; task_profiles.json describes reusable actions applied through process-group APIs.

BPF: programmable logic at hooks

eBPF programs can attach to cgroup and networking hooks and consult maps. Android uses BPF for traffic accounting, socket tagging and per-UID firewalling. A cgroup supplies a useful attachment point; it does not itself contain the policy program.

6. Zygote sandbox and process specialization

Zygote starts once, preloads common runtime state, then creates app processes quickly. Forking is only the beginning; the child must be specialized before app code runs.

initstarts Zygote
Zygote / USAPpreloaded process
Forknew child PID
SpecializeUID, GID, groups, cgroup, SELinux, mount view, limits
App processsandboxed runtime
Press Start to trace process creation.

USAP pool

Unspecialized app processes may be pre-forked. System server selects one and requests specialization, reducing startup latency.

Shared pages, separate identity

Forked processes initially share read-only/copy-on-write memory pages, but execute with their own process identity and sandbox policy.

Not a VM

Every normal app process still shares the Android Linux kernel. A kernel compromise is outside the protection promised by the ordinary app sandbox.

7. Isolated process model

Ordinary private app process

<service
  android:name=".ParserService"
  android:process=":parser"
  android:exported="false" />

Runs in a separate process but normally under the application's UID and permissions. This separates crashes and heaps, not app authority.

Isolated service process

<service
  android:name=".UntrustedParserService"
  android:isolatedProcess="true"
  android:exported="false" />

Runs with a special isolated UID and no permissions of its own. Communication is through the Service/Binder API. Give it only the data and capabilities it needs.

Select a workload.
Isolated does not mean invisible: it shares the kernel and receives data through Binder. Validate every input, keep the Binder API narrow, and do not pass broad file descriptors or privileged service handles.

8. Android Virtualization Framework and pKVM

AVF

AVF provides APIs and services for creating and managing guest VMs. VirtualizationService manages crosvm instances; Microdroid is a small Android-derived guest designed for secure payloads.

pKVM

pKVM is the ARM64 KVM-based hypervisor that places protected VMs and host Android into mutually distrusted domains. A protected VM's private memory is not readable by a compromised host Android kernel.

Host Android (EL1/EL0)
UI, app lifecycle, VirtualizationService, untrusted client
pVM A
Microdroid + security payload
pVM B
separate keys and memory
pKVM hypervisor (EL2)
page ownership, stage-2 translation, VM switching
Host-owned page: Android may access it. A protected guest may not until ownership is transferred or sharing is authorized.

Protected pVM

Confidentiality and integrity are protected even against compromised host Android, subject to the AVF threat model and hardware implementation.

Non-protected VM

Useful for compatibility, development or workload separation, but does not promise private memory from a compromised host.

Microdroid limitations

No SystemServer, Zygote, full Android Java framework, graphics UI or HAL stack. It is a focused payload environment, not another full phone UI.

Your baseline: official AVF production protection is ARM64. AOSP notes x86_64 support for non-protected testing. The x86_64 Cuttlefish capability probe may therefore PASS, SKIP, or expose only non-protected functionality depending on the image.

9. Automotive Android workload isolation patterns

Automotive security is a layered architecture problem. The correct answer is rarely “put everything in Android” or “put everything in a VM.”

Sensitive compute

Separate user/display experience

Incident 1 — The data-bill surprise

A streaming application was accidentally mapped to an OEM-funded network. Monthly connectivity cost rises sharply.

Select the control that actually determines the application’s default network.
🧨

Incident 2 — Separate process, same authority

An untrusted media parser runs with android:process=":parser". Exploitation still reaches all application permissions.

A private process separates crashes and heaps, but normally retains the app UID and authority.
🚦

Incident 3 — “High priority means safe”

A team puts a braking workload in a high-priority cgroup and declares the design functionally safe.

cgroups can improve resource governance, but they do not prove functional safety or eliminate shared-kernel risk.
🔓

Incident 4 — Host compromise matters

A key-processing service must keep long-lived vehicle secrets private even if the Android host kernel is compromised.

The host-compromise requirement changes the boundary: same-kernel isolation is not sufficient.
Debrief rule: name the asset, attacker, failure consequence, required assurance and operational cost before selecting a boundary.

PASSThe required capability exists and the expected state was observed.
SKIPThe target does not contain an optional automotive, AVF or hardware capability.
