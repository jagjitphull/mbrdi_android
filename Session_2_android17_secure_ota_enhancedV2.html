3. OTA architecture and trust boundaries

Press Play to follow a release. A green path means every independent control accepted the update.

Think of the update as a valuable package crossing eight checkpoints. A guard at one checkpoint cannot perform every other guard’s job.

The trust chain separates build provenance, offline signing, repository state, TLS server identity, campaign authorization, metadata and payload verification, inactive-slot staging, and post-boot health commitment.

ACCEPT = TLS_CA ∧ SAN ∧ CERT_TIME ∧ CALLER_ACL ∧ META_SIG ∧ META_POLICY ∧ PAYLOAD_HASH_LENGTH ∧ BOOT_SUCCESS. Failure before staging must leave the active system untouched; failure after staging must preserve a bootable fallback.

TLS

Authenticates the delivery server and protects data in transit. It does not prove that a payload remains authorized after being copied elsewhere.

Release signature

Authenticates signed metadata or payload independently of the transport channel. The device trusts a pinned or rotated public key.

Cryptographic hash

Binds metadata to exact bytes and length. A validly signed manifest must not be combined with a different artifact.

Key rule: never treat HTTPS as a replacement for payload signing, and never treat a payload signature as caller authorization. These controls defend against different attackers.

4. TLS-based delivery channels

Server-authenticated TLS

The updater validates the issuing CA, certificate time window, hostname/IP SAN and certificate chain. The lab uses a private training CA rather than disabling verification.

Client/update authorization

After TLS establishes the server channel, a bearer token, mutual TLS identity or backend-specific credential can authorize the vehicle. The lab uses a bearer token so the two decisions remain visible.

The certificate proves you reached the real warehouse. The token proves your vehicle is allowed to collect this update.

TLS validation covers CA trust, SAN/hostname binding and certificate validity. Application authorization then checks a bearer token, mTLS identity or campaign credential.

Transport decision: chain_valid ∧ name_bound ∧ time_valid. Delivery decision: transport_decision ∧ caller_authorized. Never use -k as a production fix.

5. Payload signing and hash verification

Signature verifies authority

The private release key stays in the controlled build/signing environment. Devices contain only the corresponding public verification key. Android OTA packages must be signed with a key the device expects.

Hash verifies exact content

The signed metadata contains the payload SHA-256 and length. A hash mismatch rejects truncation, corruption or replacement—even when the attacker preserves the original manifest.

The signature is the release authority’s seal. The hash is the package fingerprint. A genuine seal attached to different contents must still be rejected.

The verifier canonicalizes metadata, validates its signature with a trusted public key, enforces expiry/target/version policy, then checks payload SHA-256 and exact byte length.

Verify signature over deterministic metadata bytes before trusting any metadata field. Then bind target artifact by both digest and length to detect replacement, corruption and truncation.

6. Rollback protection and secure recovery

Boot rollback

A/B or Virtual A/B keeps the working version available while the new version is staged. If the new system fails health/boot checks, the bootloader or update stack returns to the previous working state.

Security rollback protection

AVB rollback indices prevent booting an older vulnerable image after a newer rollback index has been committed. On A/B devices, the index must not be advanced until the new slot is marked successful, or the old fallback slot could become unbootable.

Keep driving on the working lane while repairing the spare lane. Switch only after the spare lane proves safe.

Write the candidate image to the inactive slot, mark it pending, boot it with limited attempts, then mark successful or return to the previous slot.

Do not commit rollback index 2 at staging time. Commit it only after slot B is marked successful, otherwise slot A at index 1 may become ineligible before B is proven bootable.

Secure recovery principle: recovery code and keys must remain independently bootable and verified. Recovery should accept only authorized packages and must not silently bypass rollback policy.

7. Uptane framework and metadata security

Uptane uses signed roles and two repositories so one compromised key or service does not automatically authorize an arbitrary image for every ECU.

One office says “this software is genuine.” A second office says “this exact ECU is allowed to receive it.” The vehicle requires both answers to agree.

The Image repository describes authentic artifacts and hardware compatibility. The Director repository assigns artifacts to vehicle and ECU identities. Timestamp and snapshot metadata maintain freshness and consistency.

Acceptance requires valid role signatures, non-expired metadata, monotonically trusted versions, timestamp→snapshot→targets hash/length binding, Director ECU assignment, repository target agreement, and final artifact hash/length verification.

8. SWUpdate modes, ACL and update authorization

Precise terminology: SWUpdate software collections and operation modes select a subset such as stable,slot-b. Package signing authenticates sw-description and its artifact hashes. Caller/vehicle authorization is a deployment policy enforced through backend credentials, IPC/socket permissions, allowed/excluded selections and a gateway—not a property of a valid signature alone.

A genuine repair part is not enough. The mechanic must also be approved for this vehicle and this repair mode.

The signed SWU authenticates its description and artifacts. A separate gateway verifies operator signature, request expiry, vehicle ACL, selection/mode ACL and anti-downgrade policy.

AUTHORIZED = operator_sig ∧ request_fresh ∧ vehicle_acl ∧ selection_mode_acl ∧ target_version>current_version ∧ sw_description_sig ∧ artifact_hashes.

Boot Control troubleshooting — registered service, failing client

The normal trainee probe deliberately avoids the failing bootctl client path. Use this section only when an instructor wants to investigate the underlying Cuttlefish HAL/client behavior. All potentially noisy commands below suppress their expected stderr so they do not look like lab failures.

# 1. Confirm the Binder service registration.
"$ADB" -s "$SERIAL" shell \
  'service list | grep -F "android.hardware.boot.IBootControl/default" || true'

# 2. Look for the Boot Control HAL process.
"$ADB" -s "$SERIAL" shell \
  'ps -A | grep -Ei "boot.*service|hardware\.boot|boot_control" || true'

# 3. Inspect VINTF declarations for the AIDL Boot HAL.
"$ADB" -s "$SERIAL" shell '
for D in /vendor/etc/vintf /odm/etc/vintf /product/etc/vintf \
         /system/etc/vintf /system_ext/etc/vintf; do
  [ -d "$D" ] || continue
  grep -R -n -A8 -B3 "android.hardware.boot" "$D" 2>/dev/null || true
done
'

# 4. Optional silent bootctl probe. No raw error text is shown to trainees.
if "$ADB" -s "$SERIAL" shell 'bootctl hal-info' >/dev/null 2>&1; then
  echo "[PASS] bootctl can acquire the Boot Control interface"
else
  echo "[INFO] bootctl client path is unavailable on this image; property fallback remains valid"
fi

# 5. Inspect relevant logs only when troubleshooting is required.
"$ADB" -s "$SERIAL" shell '
logcat -d -b all 2>/dev/null | \
  grep -Ei "BootControlClient|IBootControl|boot.?control|bootctrl|hardware\.boot|vintf" | \
  tail -120
' || true

# 6. Optional instructor-only comparison on a userdebug image.
#    Root adbd changes the debugging context; it is NOT required for the trainee lab.
"$ADB" -s "$SERIAL" root >/dev/null 2>&1 || true
sleep 2
"$ADB" -s "$SERIAL" shell 'id' 2>/dev/null || true
if "$ADB" -s "$SERIAL" shell 'bootctl get-current-slot' >/dev/null 2>&1; then
  echo "[PASS] bootctl works with root adbd"
else
  echo "[INFO] bootctl remains unavailable with root adbd; investigate VINTF/client configuration if required"
fi

Why update_engine_client matters

Strong positive capability result: the VM exposes the real Android Update Engine client. Its help output includes operations such as --verify, --allocate, --update, --follow, --merge, --resume, --suspend and --switch_slot. This makes the image useful for studying the actual OTA control surface even though this course deliberately avoids applying a mismatched synthetic payload.
Client optionConcept to teach
--verifyCheck whether supplied payload metadata is applicable before installation.
--allocatePrepare space/resources required for the payload.
--update + --followStart and observe an OTA transaction on a correctly matched test payload.
--mergeVirtual A/B post-reboot snapshot merge lifecycle.
--suspend / --resumeControl an in-progress update lifecycle.
--switch_slotSlot switching control; understand it conceptually here rather than changing the training VM casually.
Error-free trainee rule: the main capability probe uses only commands validated to return cleanly on this Cuttlefish environment. Commands known to emit image-specific errors are either skipped or run silently in the instructor-only troubleshooting path. A trainee should therefore see PASS / INFO / SKIP classifications rather than raw bootctl or avbctl errors.
Safety boundary: these probes are intended for inspection and diagnosis. Do not change the active boot slot, mark slots unbootable, disable verification, or apply the synthetic Ubuntu training payload to Cuttlefish. A real Android OTA package must match the exact source build, target, partition layout and signing configuration.

14. Visual glossary and memory hooks

CA
Certificate Authority trusted to issue or anchor TLS certificates.
SAN
Subject Alternative Name binding a certificate to the requested DNS name or IP address.
Release signature
Cryptographic proof that authorized release metadata was signed by a trusted key.
SHA-256
A digest used here to bind metadata to exact artifact bytes.
A/B slots
Two bootable system locations that let the device stage an update without destroying its current working system.
Rollback index
A monotonic security version floor preventing an older vulnerable image from booting after commitment.
Uptane Timestamp
Freshness metadata used to detect frozen or expired repository views.
Uptane Snapshot
Metadata binding a release to consistent versions, hashes and lengths of other metadata.
Image Targets
Describes authentic artifacts, hashes, lengths and compatible hardware.
Director Targets
Assigns an artifact to specific vehicles and ECUs.
Boot Control HAL
Android HAL for A/B boot-slot state. A Binder service may be registered while a particular client such as bootctl still fails to acquire/use the interface; service registration, VINTF declaration/access, and client behavior must be diagnosed separately.
SWU
SWUpdate archive containing sw-description, its signature and referenced artifacts.
Selection, mode
A software collection and operation mode such as stable,slot-b.
